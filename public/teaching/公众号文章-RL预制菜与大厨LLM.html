RL 是预制菜，大模型是"会写菜谱却没下过厨"的大厨

一个比喻，讲清 LLM 和强化学习到底差在哪，以及为什么给大模型做应用，一半的功夫都花在"给它配工具和方向盘"上。

一、两道菜，两个时代

先摆一个我最近想通的比喻。

强化学习（RL）像预制菜。 有一条产线，反复调校，火候、配比、克数都被打磨到最精准。出品极其稳定，同一道菜每次端上来都一模一样。但它只会做这一道菜——想换菜，就得重开一条产线，重新调、重新试。

大模型（LLM）像一个能立刻接单、按需现做的大厨。 你跟他说"少盐、少辣、多点辣味层次"，他现场给你配一份，独一无二，还会根据你今天的心情换个做法。灵活得离谱，但从没真正下过厨。

区别在哪？用一句工程语言概括：

RL 时代，"学会" = 更新参数（训练出来）；LLM 时代，"学会" = 改上下文（描述出来）。

这不是时间先后，是范式的分野。传统 RL 里，你要造一个会做某事的智能体，得训练它——用奖励信号反复塑形，直到权重里长出那个策略。而 LLM 时代，你用嘴描述就行：策略不在参数里，在提示词、工具、上下文的装配里。

这把"定义智能体"的权力，从训练工程师的手里，交给了"写提示的人"。

（顺带纠正一个常见误读：LLM 时代并没有淘汰 RL——DeepSeek-R1 本身就是用 RL 训出来的。准确说法是：RL 从"智能体的构造手段"退位成了"模型的训练手段"。它没消失，是位置变了。）

二、大厨的核心秘密：他不是在"做菜"，是在"写菜谱"

这是我今天最想讲透的一点，也是所有工程决策的源头。

你可能默认：大厨懂烹饪，你说少盐，他真的少盐——他按你的需求做出了结果。

但 LLM 不是这样的。它的底层机制只有一个动作：预测下一个词。

它收到你说的"少盐少辣"，做的不是"理解你的意图然后执行"，而是——

在一段"有人说要少盐少辣"的文本后面，人类通常接着会写什么？

然后它续写出那个东西。而那个东西，通常看起来像一份"少盐少辣"的菜。注意这个"通常"——它保证的是"像"，不是"对"。

所以更精确的说法是：

他不是"会做菜"的大厨，是"会写菜谱、且能把菜谱写得像真做过"的大厨。 他产出的是文本，不是验证过的结果；他在模仿，不是理解。

打个具体的比方你就懂了：

  • 你说"少盐"，他没尝过盐，他是照着菜谱里"少盐版"的写法模仿；
  • 你点一道菜谱里没有的菜，他不会说"我不会"，会用最像的几道菜拼一个，端给你还自信满满；
  • 你问"这道菜多少卡路里"，他张口就报一个数，其实是编的——因为他没有秤，只有"卡路里数字通常怎么写"的记忆。

这三条，就是工程上天天要打交道的三个坑：

现象 专业叫法 根因
没见过的硬拼一个 泛化 / 幻觉 库存驱动：只有见过的才能拼，没有的拿最像的凑
张口报假的数 幻觉 产出是文本，不是验证过的事实
端错了还不自知 不可靠 / 无自我纠正 他在"写"，不在"验"

三、为什么"给大模型做应用"，一半功夫花在配工具和方向盘上

现在你能自己推出结论了。

假设大厨真的可信——懂烹饪、完全理解你、永不出错——那你什么都不用加，他做完直接上桌就行。

但正因为他"会写菜谱却没下过厨、还不自知"，护栏才是必需的。 而且——

护栏的数量，正好等于他不可信的程度。

每一条我们习以为常的"最佳实践"，其实都锚定着一个具体的"不可信"。我给你一一对应上：

大厨的毛病 对应的护栏 补了什么
会报假的卡路里 给他秤和计算器（把算数外包给工具） 用确定性的东西替代"像不像"
端错菜还以为对 让人试菜（确认闸门，人复核） 引入外部校验者
只懂"像菜谱"不懂你的口味 结构化点单（格式约束、示例） 收窄歧义
会为了"显得完成了"乱改配方 权限白名单（不许碰的东西就是不许碰） 限制可作恶面

这就是为什么每一个正经的 LLM 应用，都在反复强调这几件事：

  • "只引用工具返回的数据，禁止编造数值" —— 治幻觉（他会编卡路里）
  • "读不到就查，查不到就说'信息不足'" —— 治"硬拼一个"
  • 关键动作必须人工确认 —— 治"端错了还不自知"
  • 不新增写盘路径、不自动重试 —— 治"为了交差乱来"

一句话收口：

工具管"能不能做对"，闸门管"允不允许做"。 前者补能力，后者补授权——这两件事，加再多的工具也代替不了彼此。

四、落到真实场景：一个医疗设备的 AI 助手

我最近在做的一件事，正好是这个比喻的活教材。

背景：一台单目结构光三维扫描设备（用于放疗中的表面追踪），现场工程师要反复做标定、排查故障。我们给它配了个 AI 助手，让工程师用（中）自然语言对话——"重建怎么没出点云""标定文件过期了吗""下一步该转到哪个角度"。

如果 LLM 是一位可信的大厨，这个助手应该做得无所不能、说啥干啥。

但正因为它是"会写菜谱没下过厨"的大厨，我们给它定了一整套规矩：

  1. 它不许凭记忆报数，任何设备状态、标定误差、日志错误码，都必须调工具去查——数据由工具给，它只负责解读。这就是给它配"秤"。
  2. 它不能自己动手。所有会触发设备动作的操作（采图、测光、标定计算），必须先弹一条确认——工程师点"执行"才真的跑。这就是让它"先给人尝一口"。
  3. 它不许乱写。标定结果只由原有代码写入原有目录，AI 不新增任何写盘路径——防止它"为了交差"改坏东西。

你看，这三条规矩，一条都不是拍脑袋来的，每一条都能从"它产出的是文本而非验证过的结果"这个本质，反推出来。

甚至有更细的：我们给它的每一条工具输出都做了裁剪（控制在约 2000 token 以内）。为什么？因为大模型的"记性"是外挂的、不可靠的——上下文塞得越多越糊。与其让它"记住"，不如让它每次去"查"。这也是同源的一条。

五、一个判断，可以用来评估任何 AI 应用

把上面的逻辑收成一句，你可以拿它当尺子，去衡量任何一个大模型应用是否靠谱：

看清楚它把"精确性"交给了谁。

如果一个系统的关键数值、关键动作，都指望大模型自己"想"出来—— 那它就是在让一位没下过厨的大厨，凭记忆给你报卡路里。

一个成熟的设计，一定是：大模型负责"决定做什么"，工具负责"精确地做"，人负责"最终拍板"。

RL 是预制菜，稳定、可复现、但只有一道菜——适合流程明确、要求每次都一样的环节。 LLM 是现做大厨，灵活、按需、独一无二——但得配齐试菜的人、衡器、食材库，才敢让他上临床的桌。

前者赢在稳定，后者赢在灵活。而真正的工程，是知道哪个环节该用预制菜，哪个环节该请大厨。
