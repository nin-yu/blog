来源一：人类示范

第 0077 课（Lecture11 第 3 课）· 来源：lecture11.pdf p19-28 · 来源文件夹：week6-10.28 · 本课成果：掌握人类示范五步流水线、三个工程难点，理解 Mind2Web 与 OpenCUA 的四维取舍，能把团队的人工排查改造成可复用轨迹

先给结论

人类示范的五步流水线（p22）：
① 定义任务 → ② 人工执行 → ③ 记录每步 → ④ 过滤失败/噪声 → ⑤ 打包

产物格式（p22）：
Trajectory = task → (screen₁, action₁) → (screen₂, action₂) → … → (screenₙ, actionₙ)

最有价值的是那个案例对比（p28）：Mind2Web vs OpenCUA —— 同样是人类示范，两者在记录设备、环境范围、任务量、是否有推理标注上完全不同。

一、五步流水线（p22）

1  Define   在实际网站/应用上写出任务目标
2  Perform  标注员手工完成每个任务
3  Record   记录每个屏幕状态 + 点击、键盘输入
4  Filter   丢掉失败或噪声的运行，并验证成功
5  Package  存成「任务 + 步骤」对，可选带推理

输出格式：
  Trajectory = task → (screen₁, action₁) → (screen₂, action₂) → … → (screenₙ, actionₙ)

五步里有三个工程难点值得单独看：

【难点一：第 4 步「验证成功」】
  人工执行不等于执行成功
  → 必须有一个判定机制（页面状态？最终结果？）
  → 如果只靠标注员自己说"我完成了"
    → 会混入错误轨迹，训练时模型学到错的

【难点二：第 3 步「记录什么」】
  只记录"点击"不够
  → 需要屏幕状态（否则不知道点的是什么）
  → 需要输入内容（否则不知道填了什么）
  → 需要应用状态（否则无法判断结果）
  → 记录粒度决定了数据上限

【难点三：第 5 步「可选带推理」】
  人执行时脑子里有推理（"这里应该点左边那个按钮因为…"）
  但录屏录不到
  → 要么让标注员事后写（成本高、可能不真实）
  → 要么事后合成（0081 课会讲"合成推理"的风险）

二、最具启发的对比：Mind2Web vs OpenCUA（p28）

Mind2WebOpenCUA
谁记录记录工具里的众包工人标注员在自己电脑上
环境仅 Web：137 个站点，31 个域桌面：3 个 OS，200+ 应用与站点
记录内容每步的动作 + 页面快照视频、输入、可访问性树
任务数2,35022.6K
推理标注无；只有原始动作合成的，为每步添加

这张表的每一行都在做一个取舍：

【谁记录】
  众包工人（受控环境）→ 质量可控，但环境不真实
  标注员自己的电脑    → 环境真实，但质量难控、隐私风险大

【环境范围】
  仅 Web（137 站点）→ 任务聚焦、可复现；但能力面窄
  桌面（3 OS/200+ 应用）→ 覆盖广、更接近真实使用；但噪音大

【记录内容】
  动作 + 页面快照 → 数据小、易处理
  视频 + 输入 + 可访问性树 → 信息全、但体积大、处理复杂
  （视频最难处理：要从视频反推动作，见 0078 课的 VideoAgentTrek）

【任务数】
  2,350 → 精细但少
  22.6K → 多，但每条的精细度可能下降

【推理标注】
  无推理 → 数据真实（原始动作），但模型学不到"为什么"
  合成推理 → 有了"为什么"，但推理是人造的，可能与真实决策不一致
  → 这正是 0081 课"过拟合/误导"问题的来源

三、人类示范的根本限制

① 成本
   每个任务都要人亲手做一遍
   → 2,350 个任务 = 2,350 次人工操作
   → 22.6K 个任务 = 巨额人力成本

② 规模天花板
   人力是线性的
   → 不可能做到百万级
   → 而 agent 训练往往需要百万级轨迹

③ 覆盖偏差
   标注员愿意做的任务是有限的
   → 会偏向简单、常见的任务
   → 危险/复杂/长尾任务被系统性漏掉

④ 推理缺失或失真
   人的隐性推理难以记录
   → 事后补写的推理可能是"合理化"而非真实决策

→ 这四条限制直接引出后面三种来源（挖掘/合成/模拟）
→ 因为人类示范无法满足规模需求

SGRT 工程桥：你的人工作业怎么变成可复用数据

【好消息：你已经在做人类示范了，只是没记录】

现状：
  工程师排查故障 → 查日志、看图像、调参数、找到原因
  → 这就是一条完美的 trajectory
  → 但没人记录，做完就丢了

【改造方案：加一个记录环节】

第 1 步 Define（已有）
  工单系统里就是任务描述

第 2 步 Perform（已有）
  工程师真实排查

第 3 步 Record（要加）★ 唯一需要新增的动作
  排查时打开一个"记录模式"：
    每次查询工具调用 → 自动记录（时间、参数、返回摘要）
    工程师的每一步想法 → 语音或简写（"我怀疑是呼吸"）
    最终结论 → 填表单
  → 尽量自动，减少工程师负担

第 4 步 Filter（要加）
  用客观证据判断"这次排查是否成功"：
    · 处理后残差恢复正常 → 成功
    · 处理后问题复现 → 失败
  → 这个判定可以从后续数据自动得出（不需要人判断）
  ✔ 你比 Mind2Web 更有优势：你有客观的成功信号

第 5 步 Package（要加）
  存成结构化 JSON：
  {
    "task": "夜间残差升高",
    "trajectory": [ {step, action, observation, thought}, ... ],
    "outcome": {"root_cause": "...", "verified": true},
    "duration_min": 45
  }

【关键设计：推理标注怎么办】
  Mind2Web 没推理，OpenCUA 用合成推理
  你的做法：让工程师边查边说一句（语音转文字）
    · 真实（不是事后合理化）
    · 成本低（说一句话而已）
    · 比合成推理可靠得多
  → 这是你在数据质量上能超过公开数据集的地方

【不要做的事】
  ✘ 事后让工程师补写"我当时怎么想的"
    → 会变成合理化叙述，与真实决策不符
    → 这正是 OpenCUA "synthetic reasoning" 的风险

本课小结

五步：定义 → 执行 → 记录 → 过滤（验证成功）→ 打包。
产物：task → (screen₁,action₁) → … → (screenₙ,actionₙ)。
三个工程难点：如何验证成功／记录粒度决定上限／推理难记录（事后补写会失真）。
Mind2Web vs OpenCUA：众包受控 vs 真实环境；137 站点 vs 200+ 应用；2,350 vs 22.6K；无推理 vs 合成推理。
四条限制：成本高／规模线性封顶／覆盖有偏／推理缺失或失真——这引出后三种来源。

自测（先答再展开）

Q1. 人类示范的五步流水线是什么？哪一步最容易被忽略但最关键？

展开答案

① 定义任务（在真实站点/应用上写任务目标）；② 人工执行（标注员手工完成）；③ 记录（每步屏幕状态 + 点击/键盘输入）；④ 过滤（丢掉失败或噪声运行并验证成功）；⑤ 打包（存成任务+步骤对，可选带推理）。第 4 步「验证成功」最容易被忽略但最关键——人工执行不等于执行成功，如果只靠标注员自称完成，会混入错误轨迹，模型学到错的。

Q2. Mind2Web 和 OpenCUA 在四个维度上的差别是什么？各有什么取舍？

展开答案

① 谁记录：众包工人在记录工具里 vs 标注员在自己电脑上——前者质量可控但环境不真实，后者真实但质量难控；② 环境：仅 Web（137 站点/31 域）vs 桌面（3 OS/200+ 应用）——前者聚焦可复现但窄，后者覆盖广但噪音大；③ 任务量：2,350 vs 22.6K——前者精细但少，后者多但精细度可能下降；④ 推理：无（只有原始动作）vs 合成（为每步添加）——前者真实但学不到"为什么"，后者有推理但可能失真。

Q3. 人类示范的四条根本限制是什么？它们引出什么后果？

展开答案

① 成本：每个任务都要人做一遍；② 规模天花板：人力线性增长，做不到百万级而 agent 训练常需百万级；③ 覆盖偏差：标注员偏向简单常见任务，危险/复杂/长尾被系统性漏掉；④ 推理缺失或失真：人的隐性推理难记录，事后补写往往是合理化。这四条直接引出后面三种来源——从网页挖掘、合成轨迹、模拟用户与环境，因为人类示范无法满足规模需求。

Q4. 你的团队已经在做人类示范了，缺的是哪一步？推理标注该怎么解决？

展开答案

缺的是第 3 步「记录」——工程师排查时没人记录，做完就丢了。改造：加一个记录模式，自动记录每次工具调用（时间/参数/返回摘要）+ 最终结论表单；第 4 步用客观证据判断成功（处理后残差恢复正常=成功），你比 Mind2Web 更有优势因为你有客观成功信号。推理标注的解法：让工程师边查边说一句（语音转文字）——真实、成本低，比事后补写（会变成合理化）和合成推理（OpenCUA 的方式）都可靠。
