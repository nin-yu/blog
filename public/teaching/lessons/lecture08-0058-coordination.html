协调：三项基础设施 + 三种协调模式

第 0058 课（Lecture08 第 4 课）· 来源：lecture08.pdf p50-68 · 来源文件夹：week5-10.19 · 本课成果：掌握协调的基础设施（任务账本/共享记忆/工作区隔离）与三种协调模式（角色分工/资源划分/协商），理解它们如何防止冲突

先给结论

协调分两层（p52）：

基础设施 Infrastructure（提供"协作的场地"）：
　· Task Ledger 任务账本——追踪计划与执行进度
　· Shared Memory 共享记忆——召回过往经验
　· Worktree Isolation 工作区隔离——分开各 agent 的改动

模式 Patterns（决定"怎么分工"）：
　· Role Division 角色分工——谁做哪部分
　· Resource Division 资源划分——共享资源怎么分
　· Negotiation 协商——冲突方案怎么收敛

先分清：协调 ≠ 通信（p51 复习）

Communication 通信Coordination 协调
怎么交换信息怎么管理互相依赖的工作
谁收到什么、什么通道谁拥有什么任务、什么必须先做
消息格式、协议、共享产物分配、依赖、冲突解决

上一课讲通信，这一课讲协调。协调解决的是"不打架"——第 63 课列的五项代价里，"行为冲突"和"信息丢失"主要靠协调解决。

基础设施一：Task Ledger 任务账本（p53-56）

课件给了四件事（p54 原文）：

① Track the task 追踪任务
   记录目标（objective）、当前计划（current plan）、未解决的问题（unresolved questions）

② Track execution 追踪执行
   记录分配（assignments）、依赖（dependencies）、进度（progress）、阻塞（blockers）

③ Guide decisions 指导决策
   用当前状态决定接下来该跑什么

④ Support recovery 支持恢复
   执行卡住时，更新计划或重试

课件的总结句：「任务账本维护一份显式、持续更新的工作记录，用来指导 agent 之间的协调。」

代表实现：Magentic-One（p55）——编排者维护一个任务账本；Symphony（p56）——OpenAI 把 issue tracker 变成 agent 编排器。

为什么"显式"很重要：

  ❌ 隐式（账本只存在于编排者的上下文里）
     → 上下文一压缩，计划和进度就丢了
     → 外部无法观测"现在进行到哪一步"

  ✔ 显式（写成结构化文件/表格）
     → 上下文压缩不影响它
     → 人可以随时查看和干预
     → agent 崩溃重启后能恢复

这和 L06 讲的 Persistent Event Log 是同一个思想：账本在上下文之外。

基础设施二：Shared Memory 共享记忆（p57-61）

G-Memory（Zhang et al. 2025）把多 agent 的记忆分成三层（p58-59）：

┌────────────────────────────────────────────────┐
│ Insight Graph（洞见图）                          │
│   从经验中抽象出的可泛化洞见                      │
│   例："当残差集中在边缘时，优先怀疑镜头畸变"        │
└─────────────────┬──────────────────────────────┘
                  ▼
┌────────────────────────────────────────────────┐
│ Query Graph（查询图）                            │
│   编码任务查询以及它们之间的关系                   │
│   例："这次查询和上次那次是同一类问题"             │
└─────────────────┬──────────────────────────────┘
                  ▼
┌────────────────────────────────────────────────┐
│ Interaction Graph（交互图）                      │
│   agent 之间的原始交互日志（最底层、最详细）       │
└────────────────────────────────────────────────┘

三层的分工：交互图是事实、查询图是索引、洞见图是可复用知识。检索时从上层往下钻，存储时从下层往上抽象。

课件定位（p61）：「G-Memory：为多 agent 系统定制的记忆」——它比单 agent 记忆多了"agent 之间的关系"这一维。

基础设施三：Worktree Isolation 工作区隔离（p62-63）

问题与解法（p63 原文）：

问题：多个 agent 编辑同一个工作目录 → 互相覆盖

解法：
  · 给每个 agent 自己的 checkout 和 branch（独立工作区）
  · 受控整合：合并已完成的贡献、解决冲突、测试合并结果

代价：
  · 隔离减少了执行期的干扰
  · 但改动可能分叉，产生额外整合工作量

课件的取舍很清楚：隔离用"整合成本"换"执行期不打架"。值不值取决于冲突概率——冲突少则隔离是浪费，冲突多则不隔离会灾难。

三种协调模式（p64-67）

来自 CooperBench（Khatua et al. 2026）的观察：

模式课件定义解决什么冲突
Role Division 角色分工agent 就"谁处理任务的哪部分"达成一致重复劳动
Resource Division 资源划分通过划分共享资源避免碰撞同时改同一文件/同一设备
Negotiation 协商通过收敛到单一计划来解决方案冲突两种不同的解法各有道理

三者是递进的：

Role Division   → 先分好"谁做什么"（避免重复）
Resource Division → 再分好"谁能碰什么"（避免踩脚）
Negotiation     → 最后处理"我们对做法有分歧"（避免僵局）

前两个是预防性的，第三个是补救性的。

SGRT 工程桥：你的场景需要哪几项

【Task Ledger】强烈建议
  排查过程就是一次多步任务：
    · 目标：定位残差升高的根因
    · 当前计划：先图像→再呼吸→再机械→再罕见
    · 未解决问题：呼吸抖动 120ms 是否异常？
    · 已排除：图像质量、角点检测
  → 写成结构化文件（JSON/Markdown）
  → 好处：上下文爆了也不丢；人能随时看；崩了能恢复
  → 医疗场景这是合规刚需（可追溯"查过什么"）

【Shared Memory】建议但简化
  G-Memory 三层太复杂。你的场景建议：
    · Interaction 层：排查轨迹日志（已有）
    · Insight 层：案例库（"这类现象通常是什么原因"）
    · Query 层：可省略（用向量检索代替）

【Worktree Isolation】用在配置修改
  如果多个 agent 可能改配置/脚本 → 必须隔离
  如果全是只读查询 → 不需要隔离（没有冲突面）

【三种模式】
  Role Division   ✔ 必须——专家各查各的，避免重复查同一样东西
  Resource Division ✔ 必须——同一台设备的查询要串行（避免抢占）
  Negotiation     ⚠️ 慎用——医疗场景不让 agent 之间"协商"出结论
                     有分歧就上报给人，不是 agent 自己收敛

最后一条是重要的场景修正：课件的 Negotiation 假设 agent 可以自主收敛方案；你的场景不行——两个 agent 对"是不是呼吸问题"有分歧时，不能让它们自己投票决定，必须上报。

本课小结

基础设施：任务账本（显式记录，抗上下文压缩）／共享记忆（交互图→查询图→洞见图）／工作区隔离（用整合成本换执行不打架）。
三种模式：角色分工（防重复）／资源划分（防碰撞）／协商（解分歧）。
关键要求：账本必须显式且可观测，否则等于没有。
场景修正：医疗场景不让 agent 自主协商结论，有分歧上报。

自测（先答再展开）

Q1. 协调的三项基础设施是什么？各解决什么问题？

展开答案

① Task Ledger 任务账本——追踪任务（目标/计划/未解决问题）和执行（分配/依赖/进度/阻塞），指导决策和支持恢复；② Shared Memory 共享记忆——召回整个 agent 系统的过往经验；③ Worktree Isolation 工作区隔离——给每个 agent 独立 checkout 和分支，避免互相覆盖。

Q2. 为什么任务账本必须是"显式"的？隐式会有什么问题？

展开答案

显式指写在上下文之外的结构化文件/表格里。隐式（只存在编排者上下文里）会有三个问题：上下文一压缩计划和进度就丢了；外部无法观测"现在进行到哪一步"；agent 崩溃重启后无法恢复。显式账本不受上下文压缩影响，人可随时查看干预，也支持恢复。

Q3. G-Memory 的三层分别是什么？它们之间怎么配合？

展开答案

Interaction Graph 交互图——agent 之间原始交互日志（事实层，最详细）；Query Graph 查询图——编码任务查询及其关系（索引层）；Insight Graph 洞见图——从经验抽象出的可泛化洞见（知识层）。配合方式：存储时从下层往上抽象，检索时从上层往下钻取。

Q4. 三种协调模式各解决什么冲突？为什么说医疗场景要慎用 Negotiation？

展开答案

Role Division 解决重复劳动（谁做什么）；Resource Division 解决同时操作同一资源（谁能碰什么）；Negotiation 解决方案分歧（两种做法各有道理时收敛到单一计划）。医疗场景慎用 Negotiation 是因为它假设 agent 可以自主收敛结论，但医疗判断的分歧不能由 agent 投票决定——必须上报给人，否则责任无法追溯。
