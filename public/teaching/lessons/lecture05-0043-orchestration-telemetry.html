编排与可观测性：让长跑的 agent 不崩、可查

第 43 课（Lecture05 第 5 课）· 来源：lecture05.pdf p90-122 · 本课成果：理解为什么 agent 需要编排/遥测，掌握 Temporal 的执行模型（Activity/Workflow/重试/持久状态）与三种可观测性工具（MLflow / LangSmith / LangFuse）

先给结论

Agent 会长时间运行（p92-93 引 METR 的 time-horizons），支撑它的基础设施必须可靠，且需要日志/可观测性来排障。两块拼图：
① 编排 Orchestration（Temporal）——用"持久执行（durable execution）"把可能失败的动作变成可重试、可恢复、有历史状态的 work；
② 可观测性 Observability——MLflow / LangSmith / LangFuse 用来追踪与监控。

一句话：把软件工程的可靠性实践搬进 agent 工程，正是"搭 agent"和"工程化 agent"的分水岭（p122）。

为什么需要编排/遥测（p92-93）

  • Agent 运行时间长（METR 的 time-horizons 图说明任务时长在变长），支撑基础设施必须可靠。
  • 需要日志与可观测性工具来调试与监控。

Temporal 执行模型（p95-98）

Your Code (Client)
   │  调用
   ▼
[ Server ]
   ├─ Activities（可失败的功能单元）   ← Activity Workers 执行
   ├─ Workflows（把 activities 串起来） ← Workflow Workers 执行
   ├─ Execution History & State        ← 持久化的执行历史与状态
   └─ Activity Queue / Workflow Queue / Task Queue  ← 队列与调度
   Storage（存储）
概念含义
Activity"可以失败的功能单元"——把每一步做成独立可重试的单元
Workflow把 activities 连接起来（定义编排逻辑）
Execution History & State持久化的执行历史与状态——崩溃后能恢复到哪一步
Workers / QueuesActivity Workers、Workflow Workers 从队列取任务执行

核心价值：Durable Workflows（持久工作流）——p100-106 演示如何把 workflow 做成"durable"（Activities / Workflow / Worker / Run it）。

重试（p107-111）

"Retrying Flaky Activities"——对那些"时好时坏（flaky）"的 activity 自动重试。这正是把 Week4 第 38 课"多步链不会退避"这个失败模式用基础设施解决。

服务端编排（p112-117）

"Server Based Orchestration / Server Based Timing"——把编排与计时放到服务端，让长时间任务不依赖某个客户端进程活着。

可观测性工具（p118-121）

工具定位
MLflow实验/模型追踪（Databricks 生态）
LangSmithLangChain 出品，链路追踪与调试
LangFuse开源可观测性平台

小结（p122 原文）

• 编排让 agent 可靠；
• 可观测性支持调试与监控；
• 把软件工程的最佳实践与工具搬过来，会同样适用于 agent 工程；
• 搭好 evals、监控、持久执行等，正是"搭 agent"与"工程化 agent"的分水岭。

对你 SGRT 系统的含义

  1. 排查/标定流程用 durable execution：长流程某步失败能重试并从断点恢复，而不是从头再来——这是"能跑几小时不崩"的工程保障（呼应 Week2 第 21 课长程任务）。
  2. 可观测性是排障的前提：agent 出问题时，得有 trace 能看"每次模型调用/工具调用/状态变化"（对应 p125 的"让失败可观察可恢复"）。
  3. 重试要有策略：flaky 步骤自动重试，但要有上限与退避——别陷入"重复同一个失败调用"（Week4 失败模式）。

自测（先答再展开）

Q1. 为什么 agent 特别需要编排/遥测？

展开答案

因为 agent 运行时间长（METR time-horizons），支撑基础设施必须可靠，且需要日志/可观测性来排障。

Q2. Temporal 里 Activity 和 Workflow 分别是什么？"Execution History"解决什么？

展开答案

Activity 是可失败的功能单元（可重试）；Workflow 把 activities 连接起来定义编排逻辑；Execution History & State 持久化执行历史与状态，使崩溃后可恢复。

Q3. "Retrying Flaky Activities"和 Week4 哪个失败模式对应？

展开答案

对应多步链里的"Recovery 不会恢复"——重复同一个失败调用而不退避。Temporal 用基础设施层自动重试 flaky activity（配上限/退避）来解决。

Q4. 你能说出三种可观测性工具吗？对你的意义是什么？

展开答案

MLflow / LangSmith / LangFuse。意义：agent 出问题时能追踪每次模型调用、工具调用、状态变化与错误，让失败"可观察、可诊断、可恢复"。
