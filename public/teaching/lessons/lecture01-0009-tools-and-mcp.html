工具调用：一次调用的四步，和 MCP 到底省了什么

第 9 课（共 13 课）· 重建 v3 · 本课成果：能画出一“次”工具调用的完整流程，并解释 MCP 把 M×N 集成变成 M+N 的含义 · 对应第 3 课“没手”那座桥

先给结论

工具调用一次分四步：Select（选工具）→ Arguments（填参数）→ Validate（校验）→ Execute（沙箱执行）。
模型只负责前两步（决定用哪个、填什么参数），真正的校验和执行在系统侧。工具越多越杂，集成成本越高——这正是 MCP（Model Context Protocol）要解决的：把“模型↔工具”的接口标准化，使 M×N 的对接成本降成 M+N。

一次工具调用的解剖（课件 p58，配例子看）

任务：“test.py 里写了什么？”

步做什么这个例子里
① Select 选从上下文给出的工具 schema 里挑一个选中 read_file
② Arguments 填参按任务的类型化字段填参数{"path": "test.py"}
③ Validate 校验执行前做 schema 检查 / 受限解码（constrained decoding）确认 path 是 string
④ Execute 执行在沙箱里跑，结果返回上下文返回文件内容
划重点：模型出“意图”（调用哪个、给什么参），系统做“把关”（校验合法性、限制权限、沙箱执行）。这条分工线，就是后面安全设计（第 11 课）的抓手——你可以只在系统侧收紧权限，而不用担心模型“想干嘛”。

让模型自己学会用工具（两条历史线）

  • Toolformer（2023）：训练 LM 自己判断——调用哪些 API、何时调、传什么参数、怎么把结果用进回答（工具：计算器/问答/搜索引擎/翻译/日历）。
  • Gorilla（Patil 2023）：让 LLM 对接海量 API，解决“工具成千上万时怎么选、怎么填对参数”的问题。

MCP：把 M×N 变 M+N（这一节是重点）

没有统一协议时：M 个模型 × N 个工具/数据源 = M×N 套对接，每加一个都要改一遍。有了 MCP 这种标准接口：每个模型接一次协议、每个工具实现一次协议 = M+N。

无 MCP：  模型A ─X─ 工具1   模型A ─X─ 工具2   模型B ─X─ 工具1   …（M×N 条线）
有 MCP：  模型A/模型B ── MCP协议 ── 工具1/工具2/数据源        （M+N 条线）

大白话：像给所有设备统一了电源插头和插座规格——你不用为每台电器配一种插头，也不用为每个插座改线。

对照你熟悉的东西（工程桥）

  • 工具 = 你给测试台写的设备接口函数（只读的优先），普通代码，只是“谁来调”变成了 LLM 决定。
  • Validate = 接口层的参数检查与权限约束——医疗场景里，这一层是硬安全边界。
  • MCP ≈ 你们内部的统一通信协议（把“模型↔工具”想象成一组标准化的 RPC 接口）。

自测

Q1. 工具调用四步是哪四步？模型中哪几步由模型负责、哪几步由系统负责？

展开答案

Select → Arguments → Validate → Execute。模型负责 Select + Arguments（出意图），系统负责 Validate + Execute（校验与执行）。

Q2. “constrained decoding（受限解码）”用在哪一步？作用是什么？

展开答案

Validate 步（更准确说是在生成参数时就施加约束）。作用：强制生成的参数符合 schema，从源头减少非法调用。

Q3. 用一句话解释 MCP 为什么把 M×N 变成 M+N。

展开答案

因为它把“模型↔工具”的接口标准化了：模型只要实现一次协议就能接所有工具，工具也只要实现一次协议就能被所有模型调用，于是成对适配的组合数从 M×N 降到 M+N。

Q4. 医疗设备场景下，为什么“模型的意图”和“系统的把关”必须分开？

展开答案

因为安全约束不能交给模型自觉。模型可能被诱导或幻觉出危险动作，但只要系统侧的 Validate/权限/沙箱足够严（只读、白名单、需人审），就能把风险挡在执行之前。
