MCP 实战：REST 路由 → MCP 工具，只要一个 OpenAPI 规范

第 36 课（Lecture04 第 6 课）· 来源：lecture04.pdf p55-56（FastMCP + OpenAPI）+ MCP 规范 · 本课成果：看懂"用 OpenAPI 自动生成 MCP 工具"，以及"入站/出站双令牌"的鉴权写法（据课件原码）

先给结论

你不需要手写每个 MCP 工具：把后端的 OpenAPI 规范喂给 FastMCP，它会按 REST 路由自动生成对应的 MCP 工具（p55）。

鉴权要点：入站（agent→MCP server）与出站（MCP server→后端 REST API）是两套令牌，分开配置（p56）。这套模式可直接搬到你的 SGRT 设备 API：先有 OpenAPI，再一键变 MCP。

模式：REST 路由 → MCP 工具（p55）

REST routeMCP tool
GET /assignmentslist_assignments
GET /submissionsget_submissions
POST /gradepost_grade

生成代码（课件原码）：

from fastmcp import FastMCP
import httpx

api = httpx.AsyncClient(
    base_url="https://lms.stanford.edu/api/v1")

spec = (await api.get("/openapi.json")).json()

mcp = FastMCP.from_openapi(
    openapi_spec=spec,
    client=api,
    name="Course MCP",
)

# → list_assignments, get_submissions, post_grade
# 参考: https://gofastmcp.com/integrations/openapi
关键：FastMCP.from_openapi(...) 自动把 OpenAPI 里的每个 endpoint 变成一个具名工具。你只要维护好后端的 OpenAPI，工具清单就自动跟进。

鉴权：入站 vs 出站（p56）

Agent --inbound · AGENT_TOKEN--> Course MCP server --outbound · LMS_TOKEN--> LMS REST API
import os, httpx
from fastmcp import FastMCP
from fastmcp.server.auth.providers.jwt import StaticTokenVerifier

# outbound: server → LMS
api = httpx.AsyncClient(
    base_url="https://lms.stanford.edu/api/v1",
    headers={"Authorization":
             f"Bearer {os.environ['LMS_TOKEN']}"})

# inbound: agent → server
who_may_call = StaticTokenVerifier(tokens={
    os.environ["AGENT_TOKEN"]: {"client_id": "ta-agent"}})

mcp = FastMCP.from_openapi(openapi_spec=spec, client=api,
                           name="Course MCP", auth=who_may_call)
mcp.run(transport="http", port=8001)
# 参考: https://gofastmcp.com/servers/auth/token-verification

两处分权：

  • outbound（LMS_TOKEN）：MCP server 访问后端 REST API 的凭证——决定"server 能对被包装的服务做什么"。
  • inbound（AGENT_TOKEN + StaticTokenVerifier）：谁能调用这个 MCP server——决定"哪些 agent 能调工具"。

三个工程要点

  1. OpenAPI 是单一事实源：后端 API 变了，重新拉 openapi.json 即可，工具自动同步，无需手改工具定义。
  2. 两层令牌分开：别用一个令牌打通全链路——越权风险高。入站身份（谁调）和出站身份（能操作什么）要能独立撤销。
  3. transport 可选：课件示例用 transport="http", port=8001；本地也可用 stdio（子进程方式，见规范 lifecycle）。

对你 SGRT 系统的含义

  1. 设备 API 包 MCP 的捷径：如果你的标定/日志查询服务已有 OpenAPI，直接 from_openapi 生成工具，省去手写。
  2. 权限分级：只读查询用一套只读令牌（outbound），写操作（触发标定）用另一套高权限令牌，且强制人审。
  3. 审计：inbound 的 client_id（如 "qa-agent" / "troubleshoot-agent"）可用于记录"谁调了什么工具"，满足医疗合规。

自测（先答再展开）

Q1. FastMCP.from_openapi 帮你省了什么？OpenAPI 在这里的角色是什么？

展开答案

省去手写每个 MCP 工具——它按 OpenAPI 的每个 endpoint 自动生成具名工具。OpenAPI 成为"单一事实源"，后端 API 更新后重新拉取即可同步工具。

Q2. 入站和出站令牌分别管什么？为什么必须分开？

展开答案

入站（AGENT_TOKEN）管"谁能调用 MCP server"；出站（LMS_TOKEN）管"MCP server 能对被包装的后端 API 做什么"。分开是为了最小权限与独立撤销，避免一个令牌打通全链路造成越权。

Q3. 课件里 MCP server 用什么 transport？还有别的选择吗？

展开答案

示例用 http（port=8001）。也可用 stdio（子进程方式），见 MCP 规范的 lifecycle/transports。

Q4. 你的写操作工具（触发标定），鉴权和流程该怎么设计？

展开答案

用单独的写权限令牌（outbound），inbound 强制人类确认（human-in-the-loop），记录 client_id 做审计；与只读工具隔离在不同 server/凭证，降低被误用或越权风险。
