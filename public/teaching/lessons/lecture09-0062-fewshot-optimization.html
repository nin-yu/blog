Few-shot 优化：示例顺序、推理自举与 DSPy 采样

第 0062 课（Lecture09 第 2 课）· 来源：lecture09.pdf p12-22 · 来源文件夹：week5-10.21 · 本课成果：理解 few-shot 优化的两条主线（示例顺序的敏感性、推理链自举），掌握 DSPy 用拒绝采样自动挑 few-shot 的思路

先给结论

Context Optimization 的第一条线：Few-shot 优化。

两个反直觉的发现：
① 示例的顺序会显著影响结果（p15-18）——同样的例子换个顺序，准确率能差很多。
② 标注示例通常没有推理过程（p19）——但我们又需要 CoT，所以要自举（bootstrap）出推理链。

DSPy 的做法（p21）：不用微调，用拒绝采样选出成功的推理，再在 devset 上搜索最佳 few-shot 组合。

一、Few-shot 是什么，为什么能优化（p13-14）

Few-shot prompting：
  在 prompt 里放几个「输入 → 输出」的例子，让模型照着做

  例：
    Q: 2+2=?      A: 4
    Q: 5×3=?      A: 15
    Q: 英国首都?   A: 伦敦
    Q: 法国首都?   A: ← 模型在这里补

课件引 GPT-3 论文（p14）说明 few-shot 早在 2020 年就是核心能力。但能 few-shot ≠ few-shot 用得好——选哪些例子、什么顺序、要不要带推理，都是优化空间。

二、示例顺序居然影响这么大（p15-18）

Lu et al. 2022 的论文标题就很直白：《Fantastically Ordered Prompts and Where to Find Them》。

实验设置（p15）：
  · 在训练集上试很多种 prompt 顺序
  · 测这些顺序对 probing set 上标签的影响
  · 有意思的是：他们扔掉了 probing set 的真实标签
    → 说明他们找的不是"最准的顺序"，而是"最确定的顺序"

关键机制（p17）：局部熵（Local Entropy）。

高局部熵：模型对某个样本的输出概率分散
  例："the ending is universally panned" → P(负面)=0.55, P(正面)=0.45
      在 probing set 上平均后，logprobs 分布很宽

低局部熵：模型输出很确定
  例：同一个样本 → P(负面)=0.95, P(正面)=0.05

结论：有些顺序能让模型更"确定"，有些让模型更"犹豫"。论文的方法是找让模型最确定的那个顺序。

这一页的工程含义很重要：如果你随手排 few-shot 例子，你的系统可能因为"顺序不好"而表现差——但你会以为是模型能力不够。
这也解释了为什么同一个 prompt 换个人写，效果差很多。

三、Bootstrap Reasoning：没有推理链怎么办（p19-20）

问题（p19）：
  · 我们知道 CoT（思维链）很重要
  · 但标注的 few-shot 例子通常只有「问题 → 答案」，没有推理过程

需求：想要带推理的示例，但没有

方案：Bootstrap（自举）——自己造推理链

  STaR 的做法（p20）：
    1. 让模型对训练问题生成「推理 + 答案」
    2. 如果答案对了 → 保留这条推理作为示例
    3. 用保留下来的示例去训下一轮
    → 逐步积累"自己造的高质量推理"

四、DSPy：不用微调，拒绝采样就行（p21-22）

课件明确对比了 STaR 和 DSPy 的差异：

「我们甚至不需要微调；只要拒绝采样出成功的推理即可。」 
DSPy 的流程（p21）：

  ┌──────────────────────────────────────────┐
  │ 训练输入                                  │
  └────────────┬─────────────────────────────┘
               ▼
         ┌──────────┐
         │   Model  │ ──► 生成「推理 + 输出」
         └──────────┘
               ▼
         ┌──────────┐
         │  Metric  │ ──► 打分（对不对）
         └──────────┘
          ┌────┴────┐
        Keep      Discard
          │           │
          ▼           ▼
     保留这条推理   丢掉
          │
          ▼
  ┌────────────────────────────────┐
  │ 在 devset 上试各种组合，          │
  │ 找出表现最好的 few-shot 示例集     │
  └────────────────────────────────┘

和 STaR 的关键差别：STaR 把好推理拿去微调（进权重），DSPy 把好推理拿去当 prompt 里的示例（进上下文）。后者零训练成本。

五、Context Optimization 第一部分的总结（p69 前半）

Fewshot Optimization Takeaway：自举推理/输出 + 搜索有用的 few-shot 示例，是一个强有力的 prompt 优化模式。

拆开就是两件事：

  1. 自举——用模型自己生成推理链，用 metric 筛（替代人工标注）
  2. 搜索——在验证集上试不同组合，选最好的（替代手工排序）

SGRT 工程桥：你手里的"标注"其实很便宜

【你的场景】
  有大量历史案例，但大多只有「现象 → 最终处理」，没有「推理过程」

  ❌ 直接拿来当 few-shot：
     示例 = "残差 2.3mm → 重新标定"
     模型学不到"为什么"

  ✔ Bootstrap 自举：
     1. 拿 50 个历史案例，让模型生成「推理 + 结论」
     2. 用真实的历史结论当 metric 筛：
        模型说"呼吸基线漂移"，历史结论也是 → Keep
        模型说"图像质量"，历史结论是"呼吸" → Discard
     3. 保留的推理链作为 few-shot 示例
     
  【关键】你不需要人工写推理，只需要有"正确答案"来筛
          而历史 case 的最终处理结论，天然就是答案

【顺序也不能随手排】
  把"呼吸类案例"和"机械类案例"混排 vs 分组排，效果可能差很多
  → 用 20 个 case 的验证集实测，别靠直觉

本课小结

Few-shot 能优化：顺序影响很大（局部熵），别随手排。
Bootstrap：没有推理链就用模型生成 + metric 筛选，自己造。
DSPy：拒绝采样出的成功推理直接当 few-shot 示例，不用微调。
两步法：自举（造样本）+ 搜索（挑组合）——这是 prompt 优化的通用骨架。

自测（先答再展开）

Q1. "示例顺序影响结果"这个发现，工程上意味着什么？

展开答案

意味着如果你随手排 few-shot 例子，系统可能因为顺序不好而表现差，但你会误以为是模型能力不够。同一个 prompt 换个人写效果差很多，原因可能就在顺序。工程做法是用验证集实测不同顺序，或用 DSPy 这类工具自动搜索，而不是靠直觉。

Q2. 高局部熵和低局部熵分别说明什么？为什么论文要找低熵的顺序？

展开答案

高局部熵：模型对输出概率分布分散、犹豫（如 P=0.55 vs 0.45）。低局部熵：模型输出很确定（如 P=0.95 vs 0.05）。找低熵顺序是因为"确定"通常意味着模型真的抓住了任务模式，而不是在边界上摇摆；论文甚至不用 probing set 的真实标签，只按确定性来选，说明他们找的是"最稳的顺序"而非"碰巧最准的顺序"。

Q3. Bootstrap Reasoning 解决什么问题？STaR 和 DSPy 的做法有什么关键差别？

展开答案

解决"想用 CoT 但标注示例只有问题答案、没有推理过程"的问题——用模型自己生成推理链，答案对了就保留。关键差别：STaR 把好推理拿去微调（进权重，有训练成本）；DSPy 把好推理直接当 prompt 里的 few-shot 示例（进上下文，零训练成本）。

Q4. 在你的场景里，怎么用历史 case 做 bootstrap？关键是什么？

展开答案

拿一批有明确最终结论的历史案例，让模型对每个案例生成"推理 + 根因判断"，然后用真实历史结论当 metric 筛——判断一致就保留推理链作为 few-shot 示例，不一致就丢弃。关键点是：你不需要人工撰写推理过程，只需要有正确答案来筛选，而历史案例的最终处理结论天然就是答案。
