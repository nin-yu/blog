构建高效 agent：workflow 的五种模式 + 何时才该上 agent

第 22 课（Week2 第 9 课 · 毕业课）· 来源：Anthropic《Building effective agents》(2024-12) · 本课成果：把 Week2 学到的模型/训练/推理/上下文知识，落到"该用哪种编排模式"的工程判断上（与 Week1 第 12 课互为里表）

先给结论

Anthropic 的核心经验：最成功的实现，用的都是"简单、可组合的模式"，而不是复杂框架。先分清两个词：Workflow = LLM 与工具沿预定义的代码路径编排；Agent = LLM 自己动态决定流程与工具用法。判断准则：能用最简单方案就别上 agent；确实需要复杂性时，步骤固定就 workflow，需要灵活/规模化决策才 agent。

三条原则收尾：保持简单、保持透明（显式展示计划步骤）、精心做 ACI（工具文档与测试）。

一个总原则：最简优先

原文："用最简单的方案，只在必要时才增加复杂度"——这可能意味着根本不用 agent 系统。agent 系统往往用延迟和成本换任务表现，要判断这笔交易值不值。很多场景下，用检索 + 上下文示例优化过的单次 LLM 调用就够。

关于框架：可以用（Claude Agent SDK、Strands、Rivet、Vellum 等），但它们会加抽象层、掩盖底层提示与响应、让你"想加复杂度"。建议先从直接调 LLM API 开始——许多模式几行代码就能写；若用框架，务必搞懂底层（"对底层的错误假设是客户错误的常见来源"）。

积木块：增强型 LLM（augmented LLM）

最基础的单元 = LLM + 增强（检索、工具、记忆）。它有两大实现关注点：针对你的场景定制这些能力、给模型一个易用且有文档的接口。MCP（Model Context Protocol）正是把第三方工具接进来的通用做法（Week1 第 9 课）。

五种 workflow 模式（原文逐个）

① 提示链 Prompt Chaining

把任务拆成一串步骤，每步 LLM 处理上一步输出，中间可加程序化检查（gate）。适用：任务能干净地拆成固定子任务，用延迟换准确率。

例：先写营销文案→再翻译；先写大纲→检查达标→按大纲写正文。

② 路由 Routing

先分类输入，再导向专门的下游任务。作用：关注点分离、提示更专门。适用：有明显类别、且分类可准确完成（LLM 或传统分类器都行）。

例：客服问题分流；简单问题→小便宜模型（Haiku），难题→强模型（Sonnet）。

③ 并行化 Parallelization

两个变体：分sectioning（拆成独立子任务并行）与 投票 voting（同一任务多次跑取多样输出）。适用：子任务可并行提速，或需要多视角/多次尝试提升置信度。

例：一个实例答题、另一个实例做安全筛查（比同一个 LLM 兼顾两者更好）；多提示审查代码漏洞。

④ 编排者-工作者 Orchestrator-Workers

中央 LLM 动态拆解任务、分给 worker LLM、再综合结果。与并行化的关键区别：子任务不是预定义的，而是编排者按具体输入当场决定。

例：每次改多个文件的编码产品；需从多个来源搜集分析的搜索任务。

⑤ 评估者-优化者 Evaluator-Optimizer

一个 LLM 生成、另一个评估并反馈，循环迭代。适用：有清晰评估标准、且迭代改进有可测量价值。

例：文学翻译（细腻之处需评估者挑刺）；需要多轮搜索分析才能全面的复杂检索。

Agent：什么时候才用

当任务步骤数无法预测、路径无法硬编码时，才用 agent：LLM 可能运行很多轮，你必须对它的决策有一定信任。它在受信环境里适合规模化。

  • 做法：agent 通常就是"LLM 在循环里根据环境反馈使用工具"——所以工具集与文档要设计得极清晰。
  • 代价：成本更高、错误会复合。建议在沙箱里大量测试 + 恰当护栏。
  • 例：SWE-bench 编码 agent；computer-use 参考实现。

五种模式一张表

模式谁定步骤最适合你 SGRT 场景的对应
提示链代码（固定）可干净拆分的固定子任务报告生成：提取数值→对照阈值→成文
路由代码 + 分类有明确类别的输入分流日志按故障类别分流到不同处置提示
并行化代码（固定）可并行 / 需多视角多指标并行质检 + 多提示投票判异常
编排者-工作者LLM（动态）子任务无法预知故障排查：按日志内容动态决定查哪些子系统
评估者-优化者LLM（循环）有清晰评估标准、可迭代报告草稿 → 按 QA 准则挑刺 → 修订

与 Week1 第 12 课的关系

Week1 第 12 课给的是"判定法则 + 四问法"（Workflow vs Agent 的分界线）；本课给的是"确定要用 workflow 后，具体选哪种编排模式"。两课互为里表：先判范式，再选模式。实战建议：绝大多数 SGRT 工程价值来自"固定管线 + 少量 LLM 判断点"（提示链/路由/评估者-优化者），真正的开放式 agent 留给"故障排查"这类步骤未知的任务。

自测（先答再展开）

Q1. Workflow 与 Agent 的唯一本质区别是什么？

展开答案

谁决定步骤：workflow 由预定义代码路径编排；agent 由 LLM 动态决定自己的流程与工具用法。

Q2. "编排者-工作者"和"并行化"看起来像，关键区别是什么？

展开答案

子任务是否预定义：并行化的子任务是事先拆好的、固定并行；编排者-工作者的子任务由编排者按具体输入当场动态决定，不预先写死。

Q3. Anthropic 的三条核心原则是什么？

展开答案

保持 design 简单（simplicity）；保持透明——显式展示 agent 的规划步骤（transparency）；精心打造 ACI——工具文档与测试（carefully craft your agent-computer interface）。

Q4. 你的"设备故障排查"任务，该用哪种模式？为什么不是更简单的提示链？

展开答案

用编排者-工作者（或受控的 ReAct agent）——因为步骤无法预知：先查哪份日志取决于日志里有什么。提示链要求子任务能事先干净拆分，而排查是"走一步看一步"，故需要动态编排。护栏：工具只读、关键结论人审。
