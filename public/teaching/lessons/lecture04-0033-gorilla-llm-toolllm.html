工具从 5 个变成 16k 个：规模化调用怎么训

第 33 课（Lecture04 第 3 课）· 来源：lecture04.pdf p32-45 + Gorilla/ToolLLM 论文 · 本课成果：掌握"把工具体系做大"的三条路（ToolkenGPT 把工具当词、ToolLLM 训 API 检索器、Gorilla 用检索感知训练 + AST 测幻觉），并会用 p45 总表选型

先给结论

Toolformer 只有 5 个工具。真要用起成百上千个 API，需要新招：ToolkenGPT（每个工具学成一个特殊 token，触发后填参数）、ToolLLM/ToolBench（训 LLaMA + 神经 API 检索器，覆盖 16k+ 真实 API）、Gorilla（在 1.6k API 上微调，用"检索感知训练"抗低质检索，用 AST 子树匹配测幻觉）。

工程含义：当你的工具从"3 个"涨到"300 个"，瓶颈从"会不会调"变成"选不选得对 + 编不编造不存在的 API"——这正是 Gorilla 用 AST 匹配量化的东西。

路线 1：ToolkenGPT——把工具当成"词"（p32-35）

Hao et al., 2024 的思路：把每个工具表示成一个 token（"toolken"）并学一个 embedding。模型预测下一个 token 时，可能预测出一个 toolken；一旦触发，就切换到"工具模式"提示，让模型补全参数并执行。

LLM 预测下一个 token（词 或 toolken）
   → 若预测出 toolken: 生成暂停，上下文切到 tool-mode prompt（含 [tool](args) 示范）
   → 模型填参数（ICL 完成参数填充）→ 执行

p34：训练 toolken embedding 用类似"把结果 token 换成 [toolken]"的改写做损失。好处：加新工具只需学一个新 embedding，不用重训整个模型。

路线 2：ToolLLM / ToolBench——16k+ 真实 API（p37-38, p61-62）

Qin et al., 2023：

  • 从 RapidAPI 爬取 6000+ 真实世界 API，整理贴近真实的人类指令。
  • 微调 LLaMA 得到 ToolLLaMA，并配一个神经 API 检索器为每条指令推荐合适的 API。
  • 覆盖 16k+ API（p61-62 强调"16k Real APIs"）。
要点：工具一多，"该用哪个 API"本身成了检索问题——所以要配 API 检索器（本质是 Week3 的检索技术用在工具选择上）。

路线 3：Gorilla——规模化 + 抗幻觉（p40-44）

Patil et al., 2023：LLM 连接海量 API。

  • 数据（p41）：来自 HuggingFace Model Hub、PyTorch Hub、TensorFlow Hub，共 1645 个 API 调用，每条 JSON 含 {domain, framework, functionality, api_name, api_call, api_arguments, environment_requirements, example_code, performance, description}。
  • 检索感知训练 RAT（p42）：在指令微调时，故意混入正确和错误的检索结果，让模型学会"用还是忽略"检索上下文——从而对低质量检索鲁棒。推理时支持 zero-shot 或带检索。
  • AST 子树匹配测幻觉（p43）：用"抽象语法树子树匹配"判断模型生成的 API 调用是否真的对应某个存在的 API（而不是编造）。
  • 结果（p44）：准确率提升、幻觉下降。

对你 SGRT 系统的含义

  1. 工具少就直接函数调用，别上这套：你排查系统就十几个工具，用朴素函数调用 + 好描述即可（Week2 课）。规模化方案是给"几百上千 API"准备的。
  2. "幻觉工具"是真实风险：模型可能调用不存在的 API。给工具集做白名单校验（只允许调用已注册的工具），相当于 Gorilla 的 AST 匹配在工程侧的落地。
  3. 加工具 = 加检索问题：工具一旦上百，就得像 ToolLLM 那样配"API 检索器"，否则选择错误率飙升。

自测（先答再展开）

Q1. ToolkenGPT 怎么"把工具当词"？好处是什么？

展开答案

给每个工具学一个特殊 token（toolken）及其 embedding；模型预测出 toolken 就切到工具模式补参数执行。好处：加新工具只需学一个新 embedding，不必重训整个模型。

Q2. 工具数量涨到 16k 后，为什么必须配"API 检索器"？

展开答案

因为"该用哪个 API"变成了检索问题——工具太多，模型无法全部记住/正确选择，需要神经 API 检索器按指令推荐合适 API（ToolLLM 的做法）。

Q3. Gorilla 的 RAT 和 AST 匹配分别解决什么？

展开答案

RAT（检索感知训练）：训练时混入正确/错误检索结果，让模型对低质量检索鲁棒；AST 子树匹配：判断生成的 API 调用是否对应真实存在的 API，用来量化"幻觉工具"。

Q4. 你的 SGRT 排查系统有十几个工具，该不该上 ToolLLM/Gorilla 那套？

展开答案

不该——那套是给成百上千 API 准备的。十几个工具用朴素函数调用 + 好工具描述即可；但要借 Gorilla 的思路加"工具白名单校验"，防止模型调用不存在的工具。
