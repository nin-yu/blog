四种编排模式：独立、集中、去中心、混合

第 0056 课（Lecture08 第 2 课）· 来源：lecture08.pdf p16-29 · 来源文件夹：week5-10.19 · 本课成果：记住四种编排模式的通信拓扑、各自适用场景与代价，理解成本结构顺序（单 agent < 编排式 < 蜂群）

先给结论

四种编排模式（p17）：

Independent 独立——agent 之间不通信，只有一个聚合器收结果
Centralized (Orchestrator) 集中——一个编排者分别跟所有 agent 通信
Decentralized (Swarm) 去中心——所有 agent 两两互通，共享消息板
Hybrid 混合——有编排者，但 worker 之间可以直连

成本结构（p24）：单 agent < 编排式 < 蜂群。

一、Independent（p18）

   Agent 1 ──┐
   Agent 2 ──┼──► Aggregator ──► 结果
   Agent 3 ──┘
   
· agent 之间不交换中间消息
· 最后一步合并或选择各 agent 的工作

本质：这其实就是并行化（L06 讲的 parallelization），只是把"并行"落实到不同 agent 上。它的"编排"最少——没有真正的编排，只有聚合。

最适合：多个独立视角同时评估同一件事
  例：让 3 个 agent 各自审查同一份代码（安全/性能/可读性）
     → 三者不需要对话，最后汇总

不适合：后一步依赖前一步的结论

二、Centralized / Orchestrator（p19）

              ┌──► Worker 1 ──┐
Orchestrator ─┼──► Worker 2 ──┼──► Orchestrator 决定下一步
              └──► Worker 3 ──┘
              
· 编排者拆分任务、分配给专精的 agent
· worker 返回结果，编排者决定接下来发生什么

课件的取舍判断（p19 原文）：

集中监督简化了协调，但编排者可能成为瓶颈。

这个瓶颈有两种：

  • 吞吐瓶颈：所有决策都要过一次编排者，串行化。
  • 上下文瓶颈：编排者要汇总所有 worker 的结果，它自己的上下文会爆。

三、Decentralized / Swarm（p20）

   Worker 1 ◄──► Worker 2
       ▲    ╲    ╱    ▲
       │     ╲  ╱     │
       ▼      ╳      ▼
   Worker 3 ◄──► Worker 4
        （全互通 + 共享状态追踪）

· agent 可以生成子 agent
· 所有 agent 通过共享消息板或通信通道交流（all-to-all）
· 适合大规模的独立探索与发现

课件的定位很明确：「Good for large independent exploration and discovery at scale」——大规模独立探索。

关键词是"独立"。蜂群在这种场景下很强（每个 agent 探不同的方向，谁先找到算谁的）；但它也是最难控制的（见第 67 课的失败模式）。

四、Hybrid（p21）

              ┌──► Worker 1 ◄──┐
Orchestrator ─┼──► Worker 2 ◄──┼── 直连
              └──► Worker 3 ◄──┘
              
· 编排者管理整体任务并整合结果
· worker 在需要协调时直接交流
· 结合了全局监督与局部灵活，但需要明确的责任与信息共享规则

课件的判断：「结合了全局监督与局部灵活，但需要清晰的责任划分和信息共享规则」。

这个"但"是关键：混合模式把两边的优点和两边的复杂度都拿来了。没有明确规则，它会退化成"编排者管不住 + worker 乱沟通"。

成本结构（p24）

Cost Structure: Single Agent < Orchestrated < Swarms 
为什么蜂群最贵：
  · 通信是 all-to-all，消息数量随 agent 数平方增长
  · 每个 agent 都要维护自己的上下文
  · 冲突和重复工作的概率最高，需要更多 token 去协调
  · 难以提前估算总成本（拓扑是动态的）

为什么编排式居中：
  · 通信是星型，消息数量线性增长
  · 编排者的上下文是瓶颈，但至少是可观测的

为什么单 agent 最便宜：
  · 零协调开销
  · 上下文只有一份

p23 还强调：「用什么架构取决于你的任务」——没有普适最优。

动态架构（p25-28）

课件提了 DyLAN（Liu et al. 2023）：不是固定拓扑，而是运行时决定谁参与、谁跟谁连。

静态架构：agent 数量和连接关系写在代码里
动态架构：根据任务难度/进展，动态组建 agent 团队

好处：简单任务不浪费 agent
代价：动态性本身带来不可预测性（更难调试、更难估成本）

SGRT 工程桥：你的排查该用哪种

【Independent】适合：多视角并行审查
  让 3 个 agent 各自独立审查同一份标定结果
    · A 看几何一致性（重投影残差）
    · B 看时间稳定性（连续帧漂移）
    · C 看与历史案例的相似性
  → 互不通信，最后汇总成一份报告
  → 这就是 Independent，成本低、易实现

【Centralized】适合：有明确分诊的排查
  编排者先判断"问题大致在哪一类"
  → 分给对应的专家 agent（呼吸专家 / 机械专家 / 光学专家）
  → 专家返回结论，编排者整合并决定是否继续下探
  → 注意编排者上下文会累积所有专家的输出

【Swarm】不适合你的场景
  大规模独立探索（如"同时试 50 种配准参数组合"）确实适合蜂群
  但医疗场景要求可复现、可审计 → 蜂群的动态拓扑难以复现

【Hybrid】如果你要"专家之间能互相质疑"
  编排者统筹 + 专家可直接对话（"你说光学没问题，但我这里残差还是高"）
  → 需要明确规则：谁能否决谁？冲突怎么收敛？
  → 没有规则会更乱

本课小结

Independent：不通信，只聚合——并行评估多视角。
Centralized：星型，编排者协调——简化协调但有瓶颈。
Swarm：全互通——大规模独立探索，最难控也最贵。
Hybrid：编排 + 局部直连——兼顾但需要明确责任规则。
成本：单 agent < 编排式 < 蜂群；选型取决于任务而非潮流。

自测（先答再展开）

Q1. 四种编排模式的通信拓扑分别是什么形状？

展开答案

① Independent：agent 之间不通信，各自连到一个聚合器（星型但不双向）；② Centralized：编排者在中心，与每个 worker 单独双向通信（星型）；③ Decentralized/Swarm：所有 agent 两两互通（全连接/single mesh）；④ Hybrid：有编排者，但 worker 之间也可直连（星型 + 部分全连）。

Q2. Centralized 模式的"编排者可能成为瓶颈"具体指哪两种瓶颈？

展开答案

① 吞吐瓶颈——所有决策都要经过编排者，形成串行化；② 上下文瓶颈——编排者要汇总所有 worker 的结果，它自己的上下文窗口会被撑爆。

Q3. 为什么 Swarm 是成本最高的？

展开答案

① 通信是 all-to-all，消息数量随 agent 数量平方增长；② 每个 agent 都要维护自己的上下文；③ 冲突和重复工作概率最高，需要额外 token 去协调；④ 拓扑是动态的，难以提前估算总成本。

Q4. 你的排查场景里，Independent 和 Centralized 分别对应什么用法？

展开答案

Independent：让多个 agent 各自从不同角度独立审查同一份标定结果（几何一致性/时间稳定性/历史案例相似性），互不通信最后汇总——成本低易实现。Centralized：编排者先分诊判断问题大致类别，再分给呼吸/机械/光学专家 agent，专家返回结论由编排者整合并决定是否继续下探——注意编排者上下文会累积。
