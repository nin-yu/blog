复合 AI 系统：workflow 与 agent 的分界，RAG、工具、MCP

第 0006 课（Lecture01 第 6 课）· 来源：lecture01.pdf p54-59 · 来源文件夹：week1-9.23 · 本课成果：掌握 workflow 与 agent 的一句话判据，理解 RAG 三步与工具调用的四步解剖，认识 MCP 的位置

先给结论

判据只有一条（p56）：两者都是 compound AI system（LLM + 其他组件），区别在于"谁决定步骤"。
Workflow：代码固定步骤
Agent：LLM 决定步骤

三种复合形态：
RAG（p57）——连接外部知识
Tool Use（p58）——选择、填参、校验、执行
MCP（p59）——工具接入的标准化协议

一、workflow 与 agent 的分界（p56）

两者都是 compound AI systems：一个 LLM 加上其他组件。
Workflow：代码固定步骤（例：Agentless、AlphaCode 2）
Agent：LLM 决定步骤（例：SWE-agent） 
AlphaCode 2 的例子值得细看（p56）：
  · 微调 LLM 用于采样和评分程序
  · 代码执行模块
  · 为一道编程题生成最多 100 万个解，然后过滤、打分

  它很强，但步骤是代码固定的
  → 采样 → 过滤 → 评分 → 选优，全是程序写的
  → 所以是 workflow

SWE-agent 的例子：
  · 给定一个 GitHub issue
  · agent 自己决定：读哪些文件、跑什么命令、改哪里
  · 步骤是 LLM 每一步决定的
  → 所以是 agent

二、RAG 三步（p57）

1. RETRIEVE 检索
   在你的文档里搜索相关信息

2. AUGMENT 增强
   把检索到的内容加到用户问题里作为上下文

3. GENERATE 生成
   LLM 用检索到的事实回答问题

→ RAG 把 LLM 实时连接到外部知识源

三步的工程含义：

  • RETRIEVE 的质量决定上限——检索错了，后面全错
  • AUGMENT 的格式影响模型能否用好——塞一堆无关片段反而更差
  • GENERATE 要防"不按材料回答"——模型可能忽略检索结果、靠记忆答

Lecture03 会把这三步各拆成一节课讲。

三、工具调用的四步解剖（p58）

课件用一个具体例子把工具调用拆开，这是本课最有价值的一页：

任务："test.py 里有什么？"

① Select 选择
   从上下文里的工具 schema 中，选哪个工具
   → read_file

② Arguments 填参
   从任务里提取类型化的字段
   → {"path": "test.py"}

③ Validate 校验
   schema 检查、约束解码
   → path: string（调用前检查）

④ Execute 执行
   沙箱里执行，结果返回上下文
   → def add(a, b): …（返回给模型）

这四步每一步都会出问题，这就是"工具调用的失败模式"的根源（Lecture04 展开）：

步骤典型失败
Select选错工具（有多个相似工具时）
Arguments参数类型错、字段名错、值编造
Validate校验不严 → 错误进入执行
Execute超时、权限、返回格式与预期不符

四、MCP 的位置（p59）

MCP（Model Context Protocol）
→ 工具接入的标准化协议

解决的问题：
  在 MCP 之前，每个模型/框架接入工具的方式都不一样
  换个模型要重写一遍工具定义
  → MCP 定义了统一的工具描述和调用方式

和 RAG 的关系：
  RAG 把"知识"接进来
  MCP 把"能力"接进来
  两者都扩展了 LLM 的边界，但扩展的东西不同

三种复合形态的位置

          LLM Core
             │
    ┌────────┼────────┐
    │        │        │
   RAG     Tools    （Memory）
    │        │
  知识      能力
    │        │
    └── 都需要标准化接口 ──┘
              │
         MCP 在这里

SGRT 工程桥：你的系统属于哪一种

【标定流程】= workflow
  采集 → 角点检测 → 求外参 → 评估残差 → 写配置
  步骤全是代码写的
  → 即使里面用了 LLM 做某个判断，只要步骤固定就是 workflow

【排查助手】= agent
  "为什么残差升高了？" → 下一步查什么取决于上一步结果
  → LLM 决定步骤

【如果要接 RAG】
  把两年的技术文档、故障案例、设备手册做成知识库
  → 排查时检索相关案例
  → 这是 RAG，不是 agent（检索本身是被调用的一个工具）

【如果要接 MCP】
  如果将来要接入多种设备、多种数据源
  → MCP 能让"接一个新设备"变成配置而不是改代码
  → 但现在只接自家设备，没必要上 MCP

【判断口诀】
  步骤谁定？代码 → workflow；模型 → agent
  要知识？RAG；要能力？Tools；要标准化？MCP

本课小结

判据：都是 compound AI system；workflow 代码定步骤，agent 模型定步骤。
RAG 三步：检索 → 增强 → 生成；检索质量决定上限。
工具四步：选择 → 填参 → 校验 → 执行；每一步都有典型失败。
MCP：工具接入的标准化协议，解决"换模型要重写工具定义"。

自测（先答再展开）

Q1. workflow 和 agent 的判据是什么？为什么 AlphaCode 2 是 workflow？

展开答案

判据是"谁决定步骤"：代码固定步骤是 workflow，LLM 决定步骤是 agent。AlphaCode 2 虽然能生成 100 万个解并过滤评分，看起来非常智能，但整个流程（采样→过滤→评分→选优）是代码写死的，LLM 只在指定环节产出内容，不决定下一步做什么——所以是 workflow。

Q2. RAG 的三步是什么？哪一步决定系统上限？

展开答案

① RETRIEVE 检索（在文档里搜相关信息）；② AUGMENT 增强（把检索内容加到用户问题里作为上下文）；③ GENERATE 生成（LLM 用检索到的事实回答）。RETRIEVE 决定上限——检索错了后面全错。此外 AUGMENT 的格式影响模型能否用好，GENERATE 要防模型忽略检索结果靠记忆答。

Q3. 工具调用的四步解剖是什么？各举一个典型失败。

展开答案

① Select 选择（从上下文 schema 中选工具）——失败：有多个相似工具时选错；② Arguments 填参（提取类型化字段）——失败：参数类型错、字段名错、值编造；③ Validate 校验（schema 检查、约束解码）——失败：校验不严导致错误进入执行；④ Execute 执行（沙箱执行、结果返回）——失败：超时、权限、返回格式与预期不符。

Q4. 你的标定流程和排查助手分别属于 workflow 还是 agent？为什么？

展开答案

标定流程是 workflow——采集、角点检测、求外参、评估残差、写配置，步骤全是代码固定的，即使其中某一步用了 LLM 做判断，只要步骤顺序固定就是 workflow。排查助手是 agent——"为什么残差升高"的下一步查什么取决于上一步结果，方向由 LLM 决定。这个区分决定了工程做法：workflow 可复现、好调试；agent 灵活但必须配观测和兜底。
