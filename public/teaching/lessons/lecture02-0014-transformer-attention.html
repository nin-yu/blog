Transformer 与注意力：为什么上下文越长，代价越贵？

第 14 课（Week2 第 1 课）· 来源：lecture02.pdf p24-63、p85-91 · 本课成果：讲清 attention 在算什么、为什么复杂度是 O(n²)，以及它对你 SGRT 系统选型的三个直接后果

先给结论

我们把 Week1 当成"黑盒大脑"的 LLM，这周把它拆开。一句结论：Transformer 的每一层都在做"让每个 token 回头看所有前文 token"的加权求和。因为这个"人人看人人"的动作，n 个 token 要算 n² 对关系——这就是上下文昂贵、且存在"context rot"的根因。

对你的工程含义：上下文长度是钱和延迟。把 10 万 token 的日志塞给模型，比塞 1 万 token 慢约一个量级起（见第 17 课 prefill），且召回准确率会掉——所以 Week1 学的"检索/压缩/子智能体"不是锦上添花，是被架构逼出来的必需。

一句话回顾：语言模型在算什么

模型做的事是给一句 token 序列打分：P(下一个 token | 前面的 token)。采样（greedy / top-k / nucleus / 温度）只是"按分挑词"的策略。要点：

  • 它是生成模型（学数据分布、可采样），不是判别模型（只分 0/1）。
  • 训练就是让"数据里真实出现的下一个词"的预测概率越来越高——损失是交叉熵 -log P(正确词)。这一课 p93-100 的推导把"训练"翻译成了"抬高正确词的 log 概率"。

注意力在算什么（本课核心）

每个 token 的向量，乘三个权重矩阵，得到三组向量：

记号含义（大白话）在结构图里的位置（p35-39）
Q (Query)"我这个 token 想找什么信息"三路并行最上层，x≈635
K (Key)"我这个 token 能提供什么信息"中间，x≈896
V (Value)"若被选中，我实际交出的内容"x≈1137

计算式：Attention = Softmax( (Q·Kᵀ) / √dk ) · V。逐项拆：

  1. Q·Kᵀ：每个 token 的 Query 和所有 token 的 Key 做点积 → 得到一张 n×n 的"谁该关注谁"分数表。
  2. /√dk：除以维度平方根，防止数值过大导致 softmax 梯度消失（归一化尺度）。
  3. Softmax：每行归一化成概率（该 token 对全场的注意力分配）。
  4. ·V：按权重把各 token 的 Value 加权求和，得到该 token 的新表示。
工程直觉：那张 n×n 的分数表就是 O(n²) 的来源。序列翻倍，这张表变 4 倍。p61 那张对比表也点明：Transformer 相比 RNN 换来 O(1) 的串行操作（GPU 能并行训练，这是它崛起的根本），代价是 O(n²) 的序列复杂度。

一个 Transformer block 长什么样（p49-60）

      │ + 残差

      └──► [ Transformer Block ] × N 个       ← 重复 N 层

           LM Head → Softmax → 下一个 token 概率
  • Causal mask：训练时不许"偷看未来"（p37）——否则等于作弊。
  • Multi-Head：一组 WQ/WK/WV 不够，用多组并行（p44-48），不同头学不同关注模式。
  • 残差 + Layer Norm：每步把输入加回去再归一化，是深层网络能训起来的关键。

对你 SGRT 系统的三个直接后果

  1. 上下文 = 成本与延迟：n² 关系意味着长上下文不是线性变贵，而是加速变贵。设计 agent 时要主动控制"每次喂多少"。
  2. 长≠准：p84、p163 的图（RULER / OOLONG）说明长上下文下召回与聚合能力下降（context rot）。把整本手册塞进去，不如让模型"按需检索"。
  3. 选型要看架构：全 softmax attention vs 线性 attention（下层课）在长日志场景的表现和成本差很大。知道底层，才能选对模型跑你的日志排查。

自测（先答再展开）

Q1. 为什么 attention 是 O(n²)？是哪一步产生的？

展开答案

因为 Q·Kᵀ 要对"每个 token × 每个 token"算注意力分数，产生一张 n×n 表。序列长度 n 翻倍，表变 4 倍，故 O(n²)。

Q2. /√dk 和 Softmax 各起什么作用？

展开答案

/√dk：缩放点积，避免值太大让 softmax 饱和、梯度消失。Softmax：把每一行分数归一化成概率，即"这个 token 把注意力如何分配给全场"。

Q3. Transformer 相比 RNN 的核心取舍是什么？（p61）

展开答案

换到 O(1) 串行操作（GPU 可大规模并行训练，这是它取代 RNN 的根本），代价是 O(n²) 的序列长度复杂度——长上下文变贵、变难。

Q4. 你的设备日志排查 agent，为什么不该"把全量日志直接喂模型"？

展开答案

两个原因叠加：(1) O(n²) 让长日志的 prefill 成本/延迟陡增；(2) context rot 让模型在超长上下文里召回关键行更不准。正确做法是"按需检索 + 压缩"（Week1 的 RAG/压缩，Week2 第 21 课）。
