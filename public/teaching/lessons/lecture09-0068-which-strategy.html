选哪种策略：context 还是权重（Lecture09 收官）

第 0068 课（Lecture09 第 8 课Lecture09 收官）· 来源：lecture09.pdf p117-125 · 来源文件夹：week5-10.21 · 本课成果：掌握 context 优化与权重优化的取舍判据（样本效率 vs 数据需求、API 限制 vs 小模型短板），理解交替优化的策略，能为本项目选出合理路线

先给结论

课件最后给出的对比（p118-122）：

可以交替做（p118）：有时候最好的做法是先优化 prompt，再优化权重，再回来优化 prompt。

核心取舍：
Context 优化——样本效率高、跑得快、基础设施简单；但小模型可能指令跟随能力不足，且会让 prompt 越来越长
权重优化——能吃下成千上万样本持续变强；但数据饥渴、需要训练基础设施、API 模型可能不给你微调

一、交替优化（p118）

BetterTogether（Soylu et al. 2024）：有时候最好先优化 prompt，再优化权重，然后再回来优化 prompt。 
为什么交替有效：

  第 1 轮 prompt 优化 → prompt 变好，但权重还是老的
          ↓
  用新 prompt 产生的轨迹去训权重 → 权重适应了新任务
          ↓
  权重变了，原先最优的 prompt 不再是全局最优
          ↓
  再优化一轮 prompt → 找到新的最优点

  → 两者互相影响，所以交替比单次更好

二、样本效率 vs 数据需求（p119-120）

Context 优化权重优化
样本效率高（p119：GEPA 证明 prompt 优化比 RL 样本效率高得多）低（p120：数据饥渴，但能吃下成千上万样本持续变强）
典型数据量几十到几百个例子几千到几万条轨迹
迭代速度分钟到小时小时到天
上限受模型本身能力限制能突破模型原始能力

这两条结论（p119、p120）放在一起看很有意思：

Context 优化：少数据就能见效，但有天花板（模型本身的指令跟随上限）
权重优化：需要大量数据，但天花板更高（真正改变了模型能力）

→ 这决定了它们的适用阶段：
   早期 / 数据少 → context
   成熟 / 数据多 → weights

三、什么时候该用 context 优化（p121）

三条理由（p121 原文）：

① 优化 API 可访问的模型
   有些强模型不提供微调接口
   → 你只能用 context 优化

② 需要频繁、快速地重跑优化
   context 优化比权重优化跑得更快、基础设施更简单

③ 与环境交互很贵
   context 优化样本效率更高
   → 每个样本要跑一次昂贵的环境交互时，这点特别重要

四、什么时候该用权重优化（p122）

三条理由（p122 原文）：

① Context 优化失败
   尤其对小模型，有时指令跟随能力很弱
   → 怎么优化 prompt 都不行，只能改权重

② 你有能力强的教师，想要更便宜的模型
   直接蒸馏进学生模型通常很有效
   → 这是成本上的理由

③ 上下文变得太长了
   context 优化会增加 prompt 的复杂度
   → 有时需要用权重优化来避免 prompt 优化带来的 context 膨胀

第 ③ 条很微妙但很重要：prompt 优化会自我膨胀。为了覆盖更多情况，指令越来越长，示例越来越多，最后 prompt 本身成了问题。这时候把知识"压进权重"反而能释放上下文空间。

六、Lecture09 全讲总结

一、条件（p7-11）：三支柱 Data+System+Eval；五条件；五收益
二、Context 优化（p12-69）：
     · Few-shot：顺序影响大（局部熵）、Bootstrap 自举推理、DSPy 拒绝采样
     · 反思式：OPRO / MIPROv2（三步）/ TextGrad / GEPA（帕累托进化）
三、权重优化（p70-104）：
     · SFT：教师 rollout → 训学生，重多样性
     · RL：学生 rollout → 结果奖励，GRPO 省 critic
     · On-policy 蒸馏：在学生自己的状态上给教师信号
四、Agent 作为优化器（p105-116）：DGM / Meta-Harness / Auto-Research
     → metric 成为最关键控制点
五、怎么选（p117-125）：交替优化；样本效率 vs 数据需求；三条理由各一边

贯穿全讲的主线：所有优化都建立在"你有一个可信的 metric"之上。没有它，context 优化会过拟合验证集，权重要么学不到东西、要么学到错误的东西，agent 自动优化会作弊。

SGRT 工程桥：给你的项目定一条优化路线

【现状盘点】
  · 用 API 大模型（deepseek 等）→ 不提供微调
  · 有历史案例，但诊断结论的标注还不完整
  · 数据量：两年日志，够用但不是海量
  · 没有训练算力（本地只有一台开发机）

【按决策树走】
  ① 有领域数据和评估？→ 数据有，评估要补（先做这个）
  ② API 不提供微调？→ 是 → 只能 context 优化  ★ 决定性约束
  ③ 数据量少？→ 是（几十到几百案例）→ context 优化样本效率高
  ④ prompt 膨胀了？→ 还没有（刚开始优化）
  ⑤ 小模型指令跟随不足？→ 用的是大模型，不是问题
  ⑥ 有大量可验证任务 + 算力？→ 没有算力 → 暂不上 RL

【结论：第一阶段只做 context 优化】
  路线：
    Step 1  建评估集：30 个历史 case，人工标注根因对错
    Step 2  Bootstrap：让模型生成推理，用历史结论筛选
    Step 3  反思优化：挑出判错的案例，反思共同点，改指令
    Step 4  搜索组合：指令 × few-shot 组合，在评估集上选最优
    Step 5  帕累托：同时看准确率 / token 成本 / 平均轮数

【什么情况下才升级到权重优化】
  触发条件（三个之一）：
    · context 优化后准确率碰到天花板（比如停在 75% 上不去）
    · prompt 变得超过 3000 token 还在加（说明该压进权重了）
    · 需要本地部署（数据不出院）→ 必须训本地模型

  如果触发，优先选 on-policy 蒸馏（L74）：
    · 有强模型当教师
    · 训练数据集中在"本地小模型真的会犯错的地方"
    · 比 RL 采样量小得多

【绝对不能做的】
  · 让 agent 自动改"什么算诊断正确"（metric 本身）
  · 在医疗判断上跑全自动 auto-research
  · 没有可信 metric 就开始优化

这条路线的好处是每一步都可回滚、都可验证：评估集是文件、prompt 是文件、每次改动都能对比前后准确率。符合医疗设备的变更管理要求。

本课小结

交替：prompt → 权重 → prompt，两者互相影响所以交替更好。
样本效率：context 高、权重低——但权重天花板更高。
选 context：API 不给微调／需快速迭代／环境交互昂贵。
选权重：context 优化失败（小模型）／有强教师想降本／prompt 膨胀了。
前提：一切都是 metric 驱动——这是整讲的地基。

自测（先答再展开）

Q1. 为什么"先优化 prompt，再优化权重，再回来优化 prompt"这种交替策略有理？

展开答案

因为两者互相影响。第一轮 prompt 优化让 prompt 变好，但权重还是老的；用新 prompt 产生的轨迹去训权重后，权重适应了新任务；但权重变了之后，原先最优的 prompt 不再是全局最优——需要再优化一轮 prompt 找到新的最优点。单次优化只能到达局部最优。

Q2. Context 优化和权重优化在"样本效率"和"能力上限"上分别如何？

展开答案

样本效率：context 优化高（GEPA 证明比 RL 样本效率高得多，几十到几百例子就能见效），权重优化低（数据饥渴，需要几千到几万条轨迹）。能力上限：context 优化受模型本身能力限制（有天花板），权重优化能真正改变模型能力（天花板更高）。这决定了适用阶段：早期/数据少用 context，成熟/数据多用 weights。

Q3. 课件说"context 优化会增加 prompt 复杂度，有时需要用权重优化来避免 context 膨胀"——这是什么意思？

展开答案

prompt 优化会自我膨胀：为了覆盖更多情况，指令越来越长、示例越来越多，最后 prompt 本身成了占用上下文和成本的问题。这时候把知识"压进权重"（微调）反而能释放上下文空间——模型内化了这些知识就不需要每次都写在 prompt 里。所以冗余的 prompt 往往是应该转成权重优化的信号。

Q4. 为什么说"所有优化都建立在可信的 metric 之上"？四档优化各自失效的样子是什么？

展开答案

因为优化本质是"朝着 metric 指示的方向改进"，metric 错了方向就错了。四档失效样子：① context 优化会过拟合验证集（在验证集上变好、真实场景变差）；② SFT 会学到教师的错误（因为无法判断哪些轨迹是对的）；③ RL 的奖励信号是噪音，训练会崩；④ agent 自动优化会作弊（修改测试、改评测数据让指标好看）。全都指向同一个前提：metric 必须可信。
