Agent 工程最佳实践：简单、可观测、有评估、懂底层

第 44 课（Lecture05 第 6 课 · 收官）· 来源：lecture05.pdf p123-132 · 本课成果：记住四条工程铁律（保持简单 / 让失败可观察可恢复 / 跑评估 / 懂底层），理解"建→跑→评→改"的循环，以及为什么别爬通用编码榜

先给结论

四条工程铁律（p124-130）：① 保持简单（别默认上最复杂方案）；② 让失败可观察、可恢复（trace/超时/重试/预算/日志/监控）；③ 跑评估（用 eval 驱动设计决策，且用你自己的领域 eval，不是通用编码榜）；④ 懂底层（抽象让你离系统细节更远，务必知道 under the hood 在干什么）。

总纲（p130）：工程 agent 是一个循环——Build → Run → Evaluate → Improve。

铁律 1：保持简单（p124）

"Keep it Simple"——回到 p15 的框架谱系："你也许并不总是需要[最复杂的那档]"。即：先试简单方案，只在对得起时再加复杂度（呼应 Week2 第 22 课"最简优先"）。

铁律 2：让失败可观察、可恢复（p125）

• Trace：模型调用 / 工具调用 / 状态变化 / 错误
• Timeouts、retry limits、execution budgets（超时/重试上限/执行预算）
• Log outputs、diagnose failures（记录输出、诊断失败）
• Monitor the state of your system（监控系统状态）
→ 可以把错误抛回给 agent 让它重试（raise the error to the agent to try again）

要点：失败不是"异常"，而是设计对象——为失败而设计、为恢复而设计（Design for failure and recovery）。

铁律 3：跑评估（p127-128）

  • 做设计决策的最好方式是用评估来"接地"（ground them in evals）。
  • 评估让优化成为可能；建好一个 eval 是造 AI 系统最重要的一步之一。
  • 关键警告（p128）：除非你在造通用编码 agent harness 或测通用 agent 系统改进，标准编码基准不是你要爬的榜——要用你自己的领域 eval（Your Custom Domain Eval!）。
对你的直接含义：别拿"HumanEval 多少分"比你的 SGRT 排查助手。要建的是"这套 SOP/故障判定在真实数据上准不准"的领域评测集——Week1 第 10 课、Week3 第 28 课的落地。

铁律 4：懂底层（p129 Challenges / Limitations）

  • 抽象会让你离底层系统细节更远，务必知道 under the hood 发生了什么。
  • 复杂 AI 系统里很难定位失败来源——所以务必看 trace。
  • 基于框架构建会引入依赖、依赖外部库被持续维护。

总纲：工程 agent 是一个循环（p130）

Build ──► Run ──► Evaluate ──► Improve
  ▲                              │
  └──────────────────────────────┘
• Engineer Agents by Building → Running → Evaluating → Improving（是个循环！）
• 从简单开始，为新增复杂度找理由
• 为失败与恢复而设计
• 用证据与评估衡量质量、成本、延迟
• 完全理解你的系统如何工作

自测（先答再展开）

Q1. 四条工程铁律是什么？

展开答案

(1) 保持简单；(2) 让失败可观察、可恢复；(3) 跑评估；(4) 懂底层。

Q2. "让失败可观察可恢复"具体要做什么？

展开答案

Trace 模型/工具调用与状态变化和错误；设超时、重试上限、执行预算；记录输出并诊断失败；监控系统状态；必要时把错误抛回给 agent 重试。

Q3. 为什么"标准编码基准不是你该爬的榜"？你应该用什么？

展开答案

因为除非你造通用编码 harness 或测通用 agent 改进，通用基准与你的领域无关。应用自己的领域 eval（真实 SGRT 数据上的评测集）来驱动设计决策。

Q4. "工程 agent" 的核心循环是什么？对你的实际工作意味着什么？

展开答案

Build → Run → Evaluate → Improve 的循环。意味着你的 SGRT 排查助手不是一次搭成，而是从简单开始、持续用评估驱动迭代，并为失败与恢复而设计。
