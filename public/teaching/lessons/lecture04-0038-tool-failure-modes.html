工具调用会在哪儿翻车：三层失败清单 + 验收表

第 38 课（Lecture04 第 8 课 · 收官）· 来源：lecture04.pdf p67（Failure Modes in Tool Use）+ p68（Summary）· 本课成果：拿到"单次调用 / 多步链 / 对话"三层失败清单，每条配 SGRT 场景的对策，作为你自建工具系统的验收表

先给结论

工具调用的失败分三层：单次调用（选错工具/参数错/幻觉工具）、多步链（顺序错/不会退避重试）、对话（违反策略/该问却猜/不确定性）。

工程含义：每加一个工具，就照这张表逐条问"会怎么错、怎么防"。它和 Week1 第 10-11 课（可靠性/安全）、Week3 第 30 课（RAG 失败三侧）是同一套方法论——查三侧、建清单、配护栏。

失败清单（p67 原文，逐层）

一、单次调用 Single call

失败含义SGRT 场景的对策
Selection 选择错选错工具，或本不该调工具却调了工具描述写清边界、去重叠；对"无需工具"的输入做相关性检测（BFCL Relevance）
Arguments 参数错编造字段、类型/单位错用 JSON schema 强约束 + 服务端校验；参数名自解释（防呆）
Hallucinated tool 幻觉工具调用了不存在的 API工具白名单校验（只允许注册过的工具）；AST 匹配思路

二、多步链 Multi-step chain

失败含义SGRT 场景的对策
Sequencing 顺序错跳过前置调用、顺序不对在工具描述里写明前置条件；必要时用固定管线约束顺序
Recovery 不会恢复重复同一个失败调用，而不是退避（back off）加退避/换策略逻辑；失败计数 + 熔断

三、对话 Conversation

失败含义SGRT 场景的对策
Policy 违反策略在规则不允许处执行动作写清操作红线；敏感操作强制人审（MCP human-in-the-loop）
Interaction 该问却猜该向用户澄清却自行假设设计"信息不足时提问"的路径（MCP elicitation）
Non-determinism 不确定性同样的输入，时对时错用 Pass^k 验收可靠性（上节课）；固定温度、约束解码

Lecture04 总结（p68 原文要点）

✅ Why tools：补 LLM 训练没见过、或够不着的东西。
✅ Toolformer：LM 自学"调哪个 API、何时、传什么参"（自监督 + 损失过滤）。
✅ Gorilla：在 1.6k API 上训练，用 AST 匹配量化幻觉。
✅ REST / 函数调用 / MCP：从"手写请求"到"标准化接口"三代演进。

工具系统验收表（去搭你的排查助手前过一遍）

  1. 工具描述清不清？边界不重叠，参数名自解释（防选错/填错）。
  2. 有没有白名单？只允许调用注册工具（防幻觉工具）。
  3. schema 校验在不在？服务端强校验参数（防参数错）。
  4. 顺序有没有约束？前置条件写清或固定管线（防顺序错）。
  5. 失败会不会退避？退避 + 熔断（防死循环重试）。
  6. 红线定义了吗？敏感操作人审（防违反策略）。
  7. 该问会不会问？信息不足时的澄清路径（防瞎猜）。
  8. 稳不稳？用 Pass^k 测一致性（防时对时错）。

自测（先答再展开）

Q1. 工具调用的三层失败是什么？各举一例。

展开答案

单次调用（选错工具/参数错/幻觉工具）、多步链（顺序错/不会退避恢复）、对话（违反策略/该问却猜/不确定性）。

Q2. "幻觉工具"怎么防？

展开答案

工具白名单校验——只允许调用已注册的工具；Gorilla 的 AST 子树匹配也是同一思路（判断调用是否对应真实存在的 API）。

Q3. "该问却猜"对应 MCP 的哪个能力？

展开答案

Elicitation——server 主动向用户追加索要信息，让 agent 在信息不足时提问而非瞎猜。

Q4. 你的排查助手验收表里，哪一条最容易被忽略？为什么？

展开答案

"稳不稳"（Pass^k 一致性）最容易被忽略——大家只看单次能不能过，却忽略 agent 要重复运行，"时对时错"不可部署。需固定温度/约束解码并要求连续多次成功。
