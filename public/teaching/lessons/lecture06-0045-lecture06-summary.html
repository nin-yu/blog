Lecture06 总结：三个维度、三组判断

第 0045 课（Lecture06 第 8 课Lecture06 收官）· 来源：lecture06.pdf p84-86 · 来源文件夹：week3-10.12 · 本课成果：把 workflow 设计、推理行动设计、上下文设计三个维度串成一条线，掌握三组核心判断与三张速查表（Lecture06 收官）

先给结论

Lecture06 的全部内容压缩成三个维度 × 两组积木：

Workflow 设计（5 种）：Chaining／Routing／Parallelization／Orchestrator-Workers／Evaluator-Optimizer
推理/行动设计（4 种）：ReAct／Reflexion／CodeAct／先规划再执行
上下文设计（5 种）：事件日志／记忆卸载／压缩／观察遮蔽／上下文隔离

而这一切的前提是 0038 课那个判断：workflow 与 agent 的分界，在于控制流在代码还是在模型。
最后一个案例（Pi）告诉你：每一个可选项都是可以「不要」的，但每一处「不要」都有代价。

三组最有价值的判断

判断一：规划让 agent 变回 workflow（0041）

这是全讲最反直觉、也最实用的一条。

  纯 ReAct：每步依赖上步观察 → 决策分散 → 不可复现
  先规划：一次生成完整计划 → 执行按剧本 → 可复现、可并行、可审查

工程含义：
  当你想同时要「agent 的灵活性」和「workflow 的可控性」
  → 答案不是折中，是「规划 + 执行」两段分开
  → 规划段用 agent（一次决策，可回顾）
  → 执行段用 workflow（确定路径，可并行）

对医疗系统的价值：
  计划能打印给人看 → 医生能事前审核「它要查什么」
  → 这是 agent 唯一能在医疗场景被接受的方式

判断二：自评有害，外部反馈才有效（0040）

课件引的发现：让 LLM 评估自己的回答会导致性能下降

由此推出的实践原则：
  ✘ 不要在 prompt 里写「请反思你的答案是否正确」
  ✔ 要给客观信号：测试结果、数值指标、历史事实

今天的变化：
  推理模型把自纠能力训进了推理过程
  → 不需要显式 Reflexion
  → 但仍需要外部反馈来支撑推理的依据

你的场景：
  有 RMS、角点率、历史结论 → 天然的反馈源
  → 这是你比通用场景更有优势的地方

判断三：每个可选项都可以不要，但都有代价（0044）

Pi 证明了「极简也能是一个完整可用的 agent」：
  4 个工具、1 个 ReAct 循环、3 个上下文机制

但它同时证明了代价：
  没有子 agent → 长文档撑爆上下文
  没有 plan mode → 复杂任务跑偏
  没有权限检查 → 出错无边界
  没有待办清单 → 长任务忘目标
  没有后台 bash → 长命令阻塞

【关键判断法】
  不要问「要不要这个机制」
  要问「不要它，出问题时的后果我能不能承受」
  
  能承受 → 不要（省成本省延迟）
  不能承受 → 必须要（不管多麻烦）

三张速查表

表一：五种 workflow 模式何时用

模式什么时候用代价
Prompt Chaining任务复杂、可拆成有先后的步骤N 倍延迟
Routing输入有几类、需分别处理；或想省钱路由本身要准
Parallelization子任务独立（Sectioning）或多采样投票（Voting）Voting 是 N 倍成本
Orchestrator-Workers子任务数量和性质难以预判数量不可控，需设上限
Evaluator-Optimizer反馈可表述 + 评估者有能力 + 生成器能改进三条件缺一则空转

表二：四种推理模式的核心洞见

模式洞见代价
ReAct行动前先推理多轮往返
Reflexion反思有用——但必须靠外部反馈需多轮尝试 + 有客观信号
CodeAct代码是动作的好形式需沙箱、安全风险
先规划再执行规划把 agent 变回 workflow计划错了全错

表三：五种上下文模式成本排序

模式成本优先用
Observation Masking零（规则截断）⭐⭐⭐ 最先用
Persistent Event Log低（存盘）⭐⭐⭐ 必做（合规）
Memory Offloading低（存外部）⭐⭐ 中期
Context Isolation中（子 agent 跑一轮）⭐⭐ 按需
Compaction高（LLM 总结）⭐ 最后用

【你的排查助手：完整配置】

控制流（0038）
  workflow 为主，agent 嵌在诊断点
  → 采集/检测/求解/评估/写配置 = workflow
  → 根因诊断 = agent

Workflow 模式（0039）
  Chaining    ✔ 排查主流程是链
  Routing     ✔ 报警分流（分类器）
  Parallel    ✔ Sectioning 并行查四项数据
  Orchestrator ⚠️ 只用于"开放故障"场景，设 5 子任务上限
  Evaluator    ⚠️ 只做客观检查（必填字段、出处），不做主观判断

推理模式（0040-0041）
  ReAct       ✔ 诊断阶段用
  先规划       ✔ 排查前先生成计划，打印给人看，再并行执行
  Reflexion   ✔ 用 RMS/历史结论做反馈，不做自我评估
  CodeAct     ✘ 不用（Windows 环境、无沙箱、工具已结构化）

上下文（0042-0043）
  事件日志     ✔ 必做（审计 + 调试）
  观察遮蔽     ✔ 工具返回摘要而非原始日志（最先做）
  渐进披露     ✔ 技能写成 4 个文件按需读
  隔离         ✔ 读长文档时派子 agent
  压缩         ⚠️ 15 步内不需要

本课小结

三个维度：Workflow 设计（5）／推理行动设计（4）／上下文设计（5）。
判断一：规划把 agent 变回 workflow——决策集中一次，执行变可复现可并行可审查。
判断二：自评有害，外部反馈才有效；推理模型已内置自纠。
判断三：每个机制都可以不要，但要看「不要它的后果能不能承受」。
方法论：每一处取舍都用数据回答，不用直觉回答。

自测（先答再展开）

Q1. Lecture06 的三个设计维度各有哪些模式？

展开答案

① Workflow 设计 5 种：Prompt Chaining（拆步骤）、Routing（分派）、Parallelization（并行/Sectioning+Voting）、Orchestrator-Workers（动态子任务）、Evaluator-Optimizer（迭代）；② 推理/行动设计 4 种：ReAct（行动前推理）、Reflexion（外部反馈反思）、CodeAct（代码作为动作）、先规划再执行（ReWOO/LLMCompiler）；③ 上下文设计 5 种：持久事件日志、记忆卸载、压缩、观察遮蔽、上下文隔离。

Q2. 为什么「先规划再执行」对医疗场景特别有价值？

展开答案

因为规划让 agent 变回 workflow——决策集中一次、执行按剧本走，因此可复现、可并行、可审查。对医疗场景最有价值的是「可审查」：计划能打印出来给人看，医生可以事前审核「它打算查哪些项、用什么参数、按什么顺序」，如果有不该做的操作可以事前拦截。这是 agent 能在医疗场景被接受的必要形式——不能让系统跑完 20 步才让人看到它做了什么。

Q3. 三张速查表里，上下文模式的成本排序是什么？为什么必须先做观察遮蔽？

展开答案

成本排序（低到高）：Observation Masking（零成本，规则截断）→ Persistent Event Log（低，存盘）→ Memory Offloading（低，存外部）→ Context Isolation（中，子 agent 跑一轮）→ Compaction（高，LLM 总结）。必须先做观察遮蔽因为它是唯一零成本的模式——不需要调 LLM、不需要额外基础设施，只改工具返回的内容（把 5000 行日志变成「共 5000 行，ERROR 12 行，前 3 条」），就能把最大膨胀源消掉。

Q4. 「每个机制都可以不要，但都有代价」——你该怎么判断某个机制要不要？

展开答案

不要问「要不要这个机制」，要问「不要它，出问题时的后果我能不能承受」。能承受就不要（省成本省延迟），不能承受就必须要（不管多麻烦）。例如：不要子 agent → 长文档时上下文爆掉 → 可承受（可以重开）→ 可以不要；不要权限检查 → 误改照射参数导致患者受照 → 不可承受 → 必须要有。这个判断法把抽象的技术取舍转成具体的风险判断。
