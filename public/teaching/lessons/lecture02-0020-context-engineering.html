上下文工程（上）：为什么不"全塞进去"？

第 20 课（Week2 第 7 课）· 来源：Anthropic《Effective context engineering for AI agents》(2025-09) + lecture02.pdf p160-167 · 本课成果：理解"上下文是有限注意力预算"、context rot，以及 system prompt / tools / examples 各自怎么给才不臃肿

先给结论

"提示工程"正在升级为上下文工程——不再是找好词好句，而是回答"此刻该给模型看哪些 token"。核心判断：上下文是有限的注意力预算，token 越多、召回越差（context rot）。所以好上下文的定义是——用尽可能小的一组高信号 token，最大化达到目标行为的概率。

工程含义：你的 agent 好用与否，一大半取决于"每次喂什么"。这是把 Week1 的检索/记忆真正落地的技术。

从提示工程到上下文工程

提示工程 Prompt Engineering上下文工程 Context Engineering
关注怎么写好一句提示（尤其 system prompt）推理时整个 token 状态该放什么
范围单次、离散的任务跨多轮、长时间、持续演化
包含措辞系统指令 + 工具 + 外部数据(MCP) + 消息历史 + 记忆…
性质一次性写好迭代——每次决定喂什么时都要做一轮策展

Anthropic 的定义：上下文工程 = "在推理过程中，策展并维护最优 token 集合的一整套策略"，包括提示之外那些会掉进上下文的信息。

为什么重要：context rot（上下文腐烂）

  • 随上下文 token 增多，模型准确召回其中信息的能力下降（needle-in-a-haystack / Chroma "context rot" 研究）。
  • 根因是架构：Transformer 的 attention 是 n² 两两关系（第 14 课），上下文越长，注意力被拉得越薄。
  • 所以上下文是边际收益递减的有限资源——像人的工作记忆容量有限。
工程桥：这跟你的点云配准里"点太多反而拖慢收敛、还引入离群点"是一个道理——不是信息越多越好，而是信噪比。策略是 ROI 裁剪（少而准），不是把整个点云丢进去。

上下文解剖：每一块怎么给（Anthropic 四要素）

① System Prompt：找对"高度"（the right altitude）

两种失败极端：

  • 太低：把脆弱的 if-else 逻辑硬编码进提示——脆弱、难维护。
  • 太高：含糊的高层指导，不给具体信号、还假设了"共有背景"（模型并不知道）。

做法：刚好够指引、又足够灵活。用分区（<background>、<instructions>、## Tool guidance、## Output）+ XML/Markdown 分隔。目标是"完整勾勒期望行为的最小信息集"——最小不等于最短（该给的信息还是要给）。实践法：先用最小提示 + 最强模型跑，看失败模式，再针对性补。

② Tools：少而清、无功能重叠

  • 工具定义了"agents 能做什么"的契约，必须省 token + 促进行为高效。
  • 最常见失败：工具集臃肿、功能重叠、决策点含糊。连人工程师都说不清该用哪个，agent 更不可能。
  • 口诀：自包含、抗错误、用途极清晰，参数描述明确。

③ Examples：少而精，别堆边缘案例

few-shot 依然强烈推荐，但要一组多样、典型（canonical）的例子，而不是把每个边缘 case 都塞进去。对 LLM 而言，例子是"一图胜千言"。

④ Message History / Memory：动态维护

整体原则：informative, yet tight（信息充分但紧致）。运行时会不断产生新数据，必须周期性精炼（下一课的三招）。

自测（先答再展开）

Q1. 一句话说出"上下文工程"和"提示工程"的区别。

展开答案

提示工程是"怎么写好一句提示"（一次性、措辞）；上下文工程是"推理时该给模型看哪些 token"的整体策展（跨多轮、迭代、含工具/记忆/外部数据）。

Q2. 什么是 context rot？根因是什么？

展开答案

上下文 token 越多，模型准确召回其中信息的能力越差。根因是 attention 的 n² 两两关系，上下文越长注意力被摊薄，边际收益递减。

Q3. System prompt 的"两种失败极端"是什么？

展开答案

太低：硬编码脆弱 if-else 逻辑，难维护；太高：含糊、不给具体信号、还假设共有背景。要取中间"正确高度"。

Q4. 工具集最常见的失败模式？对应你设备排查 agent 的启示？

展开答案

工具臃肿、功能重叠、决策含糊——连人都说不清用哪个。启示：给排查 agent 只留少量职责清晰、互不重叠的只读工具（如 read_log / query_errorcode / get_calib_residual），别堆一大把。
