上下文工程（下）：任务比窗口长的时候怎么办

第 21 课（Week2 第 8 课）· 来源：Anthropic《Effective context engineering》(2025-09) + lecture02.pdf p171-173 + p168-169 · 本课成果：掌握三招（压缩 / 结构化笔记 / 子智能体）与"即时检索"，并知道各自适合什么任务

先给结论

当任务长到超过上下文窗口（几十分钟到几小时的连续工作），不能指望"窗口再大点"——所有窗口都会被污染。Anthropic 给三招：压缩 Compaction（把快满的对话总结后重开）、结构化笔记（把关键状态写到窗口外的文件）、子智能体（子任务在干净窗口里深挖，只回传摘要）。另加一招日常的：即时检索（just-in-time）——不提前加载全部，边做边按需取。

工程含义：这是把你的"设备排查长任务"做成能跑几小时而不崩的关键设计。

为什么不能"等窗口更大就好"

Anthropic 明确：可预见未来，任何规模的窗口都会有上下文污染与信息相关性下降的问题（context rot，上一课）。所以必须主动管理，而不是被动加长。

即时检索 vs 预先检索（p160 那一节）

两种取上下文的方式：

预先检索（pre-inference / embedding）即时检索（just-in-time）
做法推理前先把相关数据检索进来只留轻量标识（文件路径、查询、链接），运行时用工具按需加载
优点快（数据已备好）省 token、信息新鲜（绕开过期索引）
缺点可能过时/无关慢一些；需要好的工具和引导

Claude Code 用混合：CLAUDE.md 预先放进上下文，同时用 glob/grep 即时导航取文件。元数据（文件名、目录、时间戳）本身就是信号——tests/test_utils.py 和 src/core_logic/test_utils.py 用途不同，人靠目录层级理解，agent 也靠它。

长程三招（Anthropic 原文）

① 压缩 Compaction（p171 课件也讲）

做法：把临近窗口上限的对话总结压缩，用摘要重开一个新窗口。Claude Code 保留"架构决策、未解决 bug、实现细节"，丢掉冗余工具输出。

  • p171 要点：到该压缩时上下文已极长；关键决策是新窗口里留什么——留太多很快又要压缩，丢太多会丢失后来才显得关键的信息。
  • 最"轻手"的形式是清工具结果：深历史里那些原始工具输出，agent 何须再看一遍。
  • 调参建议：先在复杂轨迹上最大化召回（别漏），再迭代提升精确率（去冗余）。

② 结构化笔记（Structured note-taking / agentic memory）

做法：agent 定期把笔记写到窗口外的记忆里，之后按需读回。像 Claude Code 的 to-do 清单、或自定义 agent 的 NOTES.md。

招牌案例：Claude 玩 Pokémon——跨上千步精确记账（"最近 1234 步我在 1 号路练级，皮卡丘涨了 8 级、目标 10 级"），自发画地图、记成就、记战斗策略；上下文重置后读自己的笔记继续多小时的训练/探索。这就是"跨窗口的连贯性"。

③ 子智能体 Sub-agent 架构

做法：主 agent 只握高层计划，把深挖型子任务交给独立、干净窗口的子智能体；子智能体可能烧掉几万 token 探索，但只回传 1,000–2,000 token 的浓缩摘要。

  • 好处：关注点分离——细节搜索的上下文隔离在子体里，主 agent 专注综合。
  • 证据：Anthropic 多智能体研究系统在复杂研究任务上显著优于单 agent（对应 Week1 的多智能体）。
注意：子智能体 = 你的"分布式传感/独立标定单元"思路——各单元在本地原始数据上做重活，只向主控回传结构化摘要，而不是把原始点云全上传。

三招怎么选（Anthropic 原文）

方法最适合
压缩 Compaction需要大量来回的对话式长任务（保持对话流）
结构化笔记有清晰里程碑的迭代式开发
子智能体复杂研究/分析，并行探索有收益

加餐：别让 KV Cache 失效（p168-169）

p168-169 两页讲"顺序追加、避免让 KV Cache 失效"：如果中途改动前面的位置编码/提示，缓存全部作废（Invalidated），白付一次 prefill。含义：系统提示与工具定义放在固定位置、只做追加，是省成本又省延迟的实操习惯（呼应第 17 课）。

自测（先答再展开）

Q1. 长程三招分别是什么？各最适合什么任务？

展开答案

压缩（总结重开窗口）—适合大量来回的对话；结构化笔记（写窗口外文件）—适合有里程碑的迭代开发；子智能体（干净窗口深挖、只回摘要）—适合复杂研究/分析。

Q2. 压缩的"艺术"在哪？最轻手的形式是什么？

展开答案

艺术在于"留什么 vs 丢什么"：留太多很快要再压缩，丢太多会丢失后见之明重要的信息。最轻手的形式是清除工具调用结果（深历史里的原始输出通常不必再看）。

Q3. 即时检索比预先检索强在哪？代价是什么？

展开答案

强在省 token、信息新鲜（绕开过期索引）、可渐进发现；代价是运行时探索更慢，且需要工程上给模型配好工具与启发式引导，否则会乱用工具、跑进死胡同。

Q4. 为什么"系统提示与工具定义放在固定位置、只追加"很重要？

展开答案

因为 KV Cache 与前缀绑定（第 17 课）。中途改动前缀会让缓存失效、触发重算，白付 prefill 成本与延迟。固定位置 + 顺序追加能保住缓存命中。
