题目

为 SGRT 设备做一套工具层 + MCP 服务设计。

场景：你有一批设备能力要暴露给 agent：读标定日志、查错误码、读床板 QA 数值、触发一次标定（写操作）。请设计：

  1. 工具定义：从 Lecture04 的"工具 = LM 生成调用的外部函数"出发，写出你会给"读标定日志"这个工具定义的 name / description / inputSchema 要点（参数名怎么起、要防哪些错）。
  2. 标准接口选型：REST / 函数调用 / MCP，这套设备工具该用哪一代？为什么？如果你希望同一套工具被 IDE、聊天界面、自研 agent 共用，结论变不变？
  3. MCP 落地：画 MCP 的 Host/Client/Server 关系，说明 tools/list 与 tools/call 各做什么。你的"触发标定"工具该放在哪个 Server、要不要人审？
  4. 鉴权：说出"入站 vs 出站"双令牌分别管什么，并说明为什么写操作要用单独凭据。
  5. 失败设计：从"单次 / 多步链 / 对话"三层各挑一个你最可能踩的失败（如幻觉工具、顺序错、该问却猜），写具体对策。
  6. 验收：怎么用 Pass^k 思路验收"触发标定"这条链路的可靠性？

评判关注点（评卷时用）

  • 第 1 题：name 清晰、description 说清用途+边界、inputSchema 用 json schema 约束类型/必填；参数防呆（如强制完整设备 ID，别用模糊简称）。
  • 第 2 题：函数调用式 schema 已够；若要跨多宿主复用 → MCP。理由要落到"复用/运行时发现"。
  • 第 3 题：Host 管生命周期/权限/同意、Client 1:1 连 Server、Server 提供能力；tools/list 发现、tools/call 执行；写操作强人审（human-in-the-loop）。
  • 第 4 题：入站=agent→server（谁能调），出站=server→设备 API（能做什么）；写操作用单独凭据以最小权限+独立撤销。
  • 第 5 题：单次（幻觉工具→白名单校验 / 参数错→schema 校验）、多步链（顺序错→写前置条件）、对话（该问却猜→elicitation/澄清路径），对策具体。
  • 第 6 题：连续 k 次都成功（Pass^k），而非"试一次成功"；要求固定温度、可复现。
