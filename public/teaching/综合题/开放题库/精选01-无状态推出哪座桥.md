# 精选01 · 从"模型无状态"倒推：必须架起哪座桥？

> **精选理由**（为什么这题够格）：它只给你**一个事实**——"大模型本身无状态"——
> 却要求你从这一个点，倒推出 agent 架构里一整根承重柱的必然性。
> 答对了，你不只是知道"有 memory 这个东西"，而是理解**为什么 agent 架构长成现在这样**。
> 这是一道"架构根"级别的题，可反复回味。
>
> **牵出哪些讲**：L1（agent loop / agent memory）· L2（context engineering / 上下文成本）· L4（工具结果回填）· 横跨 RAG（跨会话记忆）。

## 题目

一句话前提：**大模型本身是无状态的（stateless）。**

所谓无状态，指单次调用就是一个纯函数 `输入 → 输出`：喂进去一段 messages，
吐出一段回复，调用结束什么都不留。它不记得上一轮说了什么、不记得刚才调过什么工具、
不记得任务做到哪一步、也不知道你昨天跟它聊过。

**请回答：只看"无状态"这一个事实，直接（且必然）推出了哪座"桥"的必要性？**

### 作答要求

1. **点根**：用一句话点出这座桥是什么（它要弥补什么根本性的缺口）。
2. **拆墩**：列出至少 3 个由"无状态"**直接派生**出的具体机制，并用表格说明
   每个机制分别在弥补无状态的哪个具体缺口（提示：不记上轮 / 工具结果会丢 / 不记进度 /
   重启即忘 / 跨会话无记忆 —— 这些缺口各需要什么）。
3. **落项目**：举一个你项目里的真实对应物（Mono-BPS BPS Copilot 或 Trio-Track 任意一处），
   说明**如果去掉这座桥会发生什么**。
4. **追问**：既然模型无状态，为什么 agent 每一轮都要把**全量**历史重新发给它，

5. **再深一层**（加分）：这件事在其他计算机系统里有没有先例？
   你能给它起一个更本质的名字吗？

## 参考解析（评卷用）

### 根：上下文管理（Context / 会话状态存储）

更本质的说法：**"用外部状态重放，把无状态函数模拟成有状态过程"** 这一整套机制。

一句话：**"无状态"是 LLM 的原罪；agent 架构的一大半，就是给它外挂一个"记忆"。**
每次调用都把完整历史重新喂进去，用"无状态函数 + 外部状态重放"伪造出"它在记着"的假象。

### 墩：由无状态直接派生的机制

| # | 无状态的缺口 | 派生机制 | 项目对应 |
|---|---|---|---|
| 1 | 不记上一轮对话 | 会话历史缓冲（messages 数组，每轮**全量**回发） | `BpsCopilot::m_messages` |
| 2 | 工具调用结果会丢 | 工具结果回填（role=tool 消息，作为下一轮输入） | `appendToolResultMessage` |
| 3 | 不记任务进度 | 外部持久化状态（进度由外部源合成后注入上下文） | `calib_progress` 三源合成 |
| 4 | 重启即忘 | 磁盘证据重建（从文件/产物反推状态） | `Pose_*.bmp` 编号 → 推断下一步 |
| 5 | 跨会话无记忆 | 长期记忆 / RAG 知识库（外挂检索） | memory 工具 / `kb_search` |
| 附 | 上下文窗口有限 | token 裁剪 / context engineering | 工具输出 < 2K token 裁剪 |

**因果链要清晰**：不是"agent 有 memory 功能"，而是"**因为无状态，所以必须外置 memory**"。
每一个机制都能从"无状态"这个根上推导出来，而不是并列地背下来。

### 落项目（以"重启后标定能接着做"为例）

模型完全不知道上次做到哪一步。所以 `calib_progress` 必须去
**磁盘证据（`Pose_*.bmp` 最大编号）+ 面板实时态（`m_guideStage`）+ 标定产物时间戳**
三处取交集，重新算出来，再注入上下文。

**去掉这座桥的后果**：不注入进度 → 模型重启后只能从零"猜" → 跳步/漏步（比如重复采集已完成的
位置 3，或跳过位置 4 直接进位置 5）。这正是设计文档 §7.4「状态来源：重启后仍能接着做」存在的理由。

### 追问：为什么要发全量历史 + 上下文窗口约束

因为模型无状态，它**看不到**上一轮的 messages —— 在它视角里每次调用都是"第一次"。
所以必须把全部历史（system + 所有 user/assistant/tool 消息）**原样重发**，它才"记得"。

约束：这直接逼出**上下文窗口上限**问题 —— 历史越长 token 越多，于是必须有
① 窗口够大的模型（如 1M 上下文），或 ② 截断 / 摘要 / 裁剪策略（context engineering），
否则长任务会溢出。这也解释了为什么工具输出要压缩（<2K token/次）。

**延伸**：这正是 L2「上下文成本（O(n²) attention / Prefill / KV Cache）」要解决的问题 ——
每轮重发全量，意味着第 n 轮的 prefill 成本随历史线性增长，attention 更是随序列长度平方增长。

### 加分项：本质命名 / 先例

这本质是计算机科学的**老套路**：

- **HTTP 无状态 + session 存储**：服务器不记你，靠 cookie/session 每次带上你是谁。
- **函数式编程**：用显式传递的 state 模拟可变状态，而不是靠隐藏的变量。
- **REST 架构**：无状态是刻意设计，把"状态"推给客户端或外部存储。

一句话本质名：**"无状态计算 + 外部状态存储 = 有状态行为"**。
LLM agent 只是这个老思想在新场景下的又一次应用。

## 评判关注点

- ✅ **抓根**：是否抓住"桥 = 上下文管理 / 外部状态重放"这个根，而不是只罗列 memory 功能。
- ✅ **因果**：派生的机制是否**真的从"无状态"推出来**（因果链清晰），而非并列背知识点。
- ✅ **落地**：项目对应物是否具体、去掉后后果是否说对（体现"设计决策有代价"的意识）。
- ✅ **反直觉点**：第 4 问是否理解"每轮全量重发"及其对上下文窗口的约束。
- ⭐ **加分**：能把它抬到"无状态计算 + 外部状态存储"这个本质，并举出 HTTP/REST/FP 先例。
