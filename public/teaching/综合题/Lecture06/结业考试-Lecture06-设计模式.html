结业考试 · Lecture06 · Agent 设计模式与脚手架

来源：CS329Z lecture06 课件《Agent Design Patterns and Scaffolds》（Diyi Yang / Michael Ryan / John Yang）· 源文件夹 week3-10.12

覆盖：p8-86（workflow vs agent / 五种 workflow 模式 / 推理设计四法 / 五种上下文管理模式 / Pi 案例）

作答方式：直接在下方「我的作答」区写，用你自己的话，答完对我说"评卷"。

题目

你所在的团队要做一个 「SGRT 标定漂移自动排查助手」：每天放射治疗开始前，系统自动检查上一夜的标定状态，如果发现漂移超阈值，就自动排查根因并给出报告（不自动修改任何参数，只出报告给人确认）。

已知条件：

  • 可用的查询工具：查标定日志、查外参文件、查呼吸曲线原始数据、查 kV 图像、查设备维护记录、查历史相似案例库。
  • 已知的漂移原因分布（来自过去两年的统计）：
  • 45% 呼吸信号基线漂移
  • 25% 床板机械位置变化
  • 18% 相机支架热变形
  • 12% 其他罕见原因
  • 合规要求：每一个排查步骤、每一次读取的数据、每一个判断，都必须可追溯、可复现。
  • 安全边界：助手绝对不能修改任何会影响照射的参数。

请回答下面 6 个问题。每题都要说清 "为什么"，只列名词不算通过。

问题 1 · 范式判定（对应第 45 课）

这个助手应该是 workflow 还是 agent？还是两者的组合？

请给出判定，并说明：

  • 你的判定依据是什么（用"控制流在哪"这个判据来论证）；
  • 如果是组合，请明确指出 哪一部分用 workflow、哪一部分用 agent，以及分界线画在哪。

问题 2 · workflow 模式选型（对应第 46 课）

假设排查流程里有一个"初步分类"环节：根据漂移的特征，把这次异常分到上面 4 类原因之一，然后走对应的深入排查路径。

  • 这个环节最适合用五种 workflow 模式里的哪一种？为什么？
  • 在处理这个分类时，如果把 45% 的"呼吸基线漂移"用最轻量的路径处理、把 12% 的"罕见原因"用最详尽的路径处理，这属于什么设计思想？带来什么收益、什么风险？

问题 3 · 推理与行动（对应第 47、48 课）

排查助手要做的第一件事是查明"残差 RMS 从 0.9mm 涨到 2.4mm"的原因。

  • 请描述它会用的 ReAct 式循环：写出前 2-3 轮的 Thought / Action / Observation（用上面给的工具，动作要具体可行）。
  • 假设第 1 轮查完发现"图像质量正常"，助手得出"应该不是图像问题"这个结论。这个结论是否可信？为什么？（提示：想想 Reflexion 那一课讲的"自反思的局限"）
  • 要让反思真正有效，反馈必须满足什么条件？

问题 4 · 行动形式（对应第 49、50 课）

排查中有一个环节要处理 过去 7 天、每天 20 帧、共 140 帧的 kV 图像（每帧大约 2000×2000 灰度图），要统计"角点检测成功率"和"角点分布覆盖面积比"。

  • 用 JSON 行动和用 代码行动，分别会发生什么？请具体说明上下文规模上的差别。
  • 这个任务适合"先规划再执行"（ReWOO 式）还是"边想边走"（ReAct 式）？为什么？

问题 5 · 上下文管理（对应第 51、52 课）

这个助手一次排查可能走 15-20 步，每步都查数据。请设计它的上下文管理方案：

  • 五种上下文管理模式（事件日志 / 记忆卸载 / 压缩 / 观察遮蔽 / 隔离）里，哪几种你会用？分别用在哪一环？
  • 哪一种对你这套系统是"合规硬要求"而不是"效率手段"？为什么？
  • 请回答：如果为了省 token 把某一步的原始数据删掉了，会不会违反合规要求？正确的做法是什么？

问题 6 · 案例借鉴（对应第 53 课）

Pi 的四个设计选择是：工具极简（只给 read/bash/edit/write）、ReAct 循环、树形上下文、无权限弹窗（auto-mode）。

请逐条判断：哪些可以借鉴到你的排查助手，哪些绝对不能？ 对每一条给出理由。

特别说明：你现在的判断如果只是"医疗设备要安全所以要加权限"，请说得更具体——权限该加在哪一层、为什么加在那一层、加了之后对 agent 的能力有什么损失。

评判关注点（评卷用）

这一节是给我评卷用的，作答时可以不看。

问题 1

  • ✅ 必须用"控制流在哪"作判据，而不是"复杂不复杂"。
  • ✅ 正确答案是组合：初步筛选/阈值判定/报告生成 → workflow（程序化；可复现、合规）；根因排查 → agent（不知道是哪个原因，必须边查边定方向）。
  • ✅ 分界线应该在"是否修改任何东西"和"是否需要探索"两处：安全动作一律 workflow，探索一律 agent。
  • ⚠️ 只说"用 agent 因为比较智能" = 没抓住判据。
  • ⚠️ 说"全用 workflow"要看他怎么处理 4 类原因 + 罕见原因——如果他能设计出完整决策树（含"其他"兜底），可以接受，但要指出维护成本高、新增原因要改代码。

问题 2

  • ✅ 正确答案：Routing。因为 4 类原因是可以事先枚举的离散类别，且类别间处理路径差异大。这正是 routing 的适用条件。
  • ✅ 第二问考的是 routing 的核心价值 = 成本优化（大多数走轻路径、少数走重路径），以及风险 = 分类器错了后面全错。
  • ✅ 加分项：指出"分类器本身要有评估集"、"要允许'不确定'这一档兜底"、"45%/12% 是可测的先验分布，可用于设计权重"。
  • ⚠️ 说"用 orchestrator-workers" = 混淆了 routing 和动态拆解，要扣。
  • ⚠️ 只说"能省钱"不说"分类错误的风险" = 半懂。

问题 3

  • ✅ ReAct 循环要具体：比如
  • Thought: 先看图像质量还是先看呼吸？→ 先看最可能且最便宜的那个
  • Action: 查最近 7 天 kV 图像质量指标
  • Obs: 角点识别率 98%，图像质量正常
  • Thought: 排除图像来源，转向呼吸信号
  • Action: 查呼吸曲线呼气末识别时刻
  • Obs: 抖动 120ms（正常 <50ms）
  • ✅ 第二问关键："图像质量正常"是观察，"应该不是图像问题"是推断——后者可能错（比如图像质量指标好但角点分布偏）。而且这句推断如果由同一个模型做出，就是自我评价，不可靠。
  • ✅ 第三问：反馈必须来自外部环境的客观信号（算出来的 RMS、代码断言、测试结果），不能是"模型觉得自己对"。
  • ⚠️ 只描述循环不说"为什么反思有效" = 漏了 Reflexion 的核心。
  • ⚠️ 认为"模型自己判断就行" = 直接踩了 p41 的坑。

问题 4

  • ✅ JSON 方案的致命问题要说清：140 帧 × 每帧的角点坐标（假设 48 个点 × 2 坐标），如果每帧结果都进上下文，第一帧就可能几千 token，140 帧直接爆窗口。即使是摘要统计，140 次往返也是 140 次模型调用。
  • ✅ 代码方案：一次生成一段循环代码，中间结果留在执行环境的变量里，只把最终统计（2-3 个数）带回上下文。差异是几个数量级。
  • ✅ 第二问：适合先规划。因为检查项固定（成功率、覆盖面积比）、无依赖分支、可并行——计划能事先排好。
  • ⚠️ 只说"代码更方便"不说上下文规模 = 没答到点上。
  • ⚠️ 说"适合边想边走"且理由是"不知道结果" = 没理解这个任务是统计型不是探索型。

问题 5

  • ✅ 事件日志（Persistent Event Log）是合规硬要求——这是本题最重要的判别点。医疗设备要求可追溯、可复现，"谁在什么时候查了什么、得出什么判断"必须原样留档。
  • ✅ 其余四种是效率手段：卸载（把"已排除的假设"结构化存起来）、压缩（对排查过程摘要）、遮蔽（旧原始数据只留结论）、隔离（大范围日志检索交给子 agent）。
  • ✅ 第三问关键：不能直接删。正确做法是"事实与呈现分离"——事件日志里原样保留，只对"给模型看的上下文"做裁剪/摘要/遮蔽。因为日志是账本，上下文是视图。
  • ⚠️ 说"为了省 token 可以删原始数据" = 严重问题，合规风险。
  • ⚠️ 认为五种都要用 = 没有区分"必需"和"手段"。

问题 6

逐条判断：

| Pi 的做法 | 正确判断 | 关键理由 |

|---|---|---|

| 工具极简（只给 bash） | ❌ 不能照搬 | 医疗软件要求每个动作有明确语义、可审计、可复现。bash 的能力边界无限，无法为每个动作定义语义和日志。应该少量专用工具 + 严格参数校验。加分：指出"工具少"这个思路可以借鉴（避免工具膨胀），但形式不能照搬。 |

| ReAct 循环 | ✅ 可以借鉴 | 排查是探索型任务，先想再查再修正正是需要的形态。 |

| 树形上下文 | ✅ 可以借鉴（有条件） | 试错不污染主线，这对排查很有价值。但要注意：分叉记录本身也要进事件日志（否则不可追溯）。 |

| 无权限弹窗 / auto-mode | ❌ 绝对不能 | 必须加硬闸门。关键要求他答出"加在哪一层"：不是加在 agent 的 prompt 里（模型可以被说服），而是加在工具执行层/系统调用层——任何写操作在真正执行前被拦截，与模型说了什么无关。 |

  • ✅ 加分项：提到"只读工具不需要权限闸门，写工具必须"——这是正确的分层。
  • ✅ 加分项：指出损失是"自动化程度下降，需要人确认"，但这是必须付的代价。
  • ⚠️ 只说"要加权限"不说加在哪层 = 半懂。
  • ⚠️ 认为"prompt 里写'不要修改参数'"就够了 = 严重错误（这是 Lecture01 就讲过的边界问题）。
