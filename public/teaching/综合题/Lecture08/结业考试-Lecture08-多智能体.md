## 场景
你的排查助手现在是单 agent：一个模型 + 6 个工具，循环诊断。单次排查平均 8 轮、耗时 3 分钟、成功率约 72%。

有人提议改成多 agent：
- 一个「协调者」拆解问题
- 「图像 agent」「呼吸 agent」「机械 agent」各查一块
- 一个「汇总者」综合结论

## 题目

**Q1（判据，20 分）**
课件给了单 agent 与多 agent 的判据，以及多 agent 的四项收益、五项代价。
（a）列出这四项收益和五项代价。
（b）用课件给的判据判断：上面的提议该不该做？说明你的判断依据。
（c）课件有一条建议是「先建单 agent 基线」。如果现在的 72% 成功率的单 agent 已经存在，这条建议还适用吗？为什么？

**Q2（编排模式，25 分）**
课件讲了四种编排模式。
（a）上面的提议属于哪种（或哪几种）模式？说明理由。
（b）四种模式各自的适用条件和代价。
（c）如果坚持要多 agent，你会怎么改造这个提议？说出你的具体调整和理由。

**Q3（通信与协调，25 分）**
（a）课件强调 handoff 与 agent-as-tool 有关键差别。这两者的差别是什么？各适合什么场景？
（b）你的场景该用哪个？为什么？
（c）多 agent 协调需要「任务账本」。账本里该记什么字段？为什么这几个字段是必须的？
（d）工作区隔离在你的场景里意味着什么？不隔离会有什么问题？

**Q4（失败模式与评估，20 分）**
（a）课件列了三类多 agent 失败模式。逐条说明它们在你的场景里会怎么表现。
（b）多 agent 系统的评估比单 agent 难在哪？你该怎么测「是哪个 agent 出错」？
（c）成本上，这个提议会让单次排查的 token 消耗变成多少（估算）？这个代价能接受吗？

**Q5（SGRT 落地，10 分）**
给出你的最终方案：单 agent 还是多 agent？如果是单 agent，怎么改进它的 72%？如果是多 agent，怎么编排？必须给出具体的模块划分和每个模块的职责边界。
