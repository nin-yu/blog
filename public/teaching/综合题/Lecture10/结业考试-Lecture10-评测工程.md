## 场景
你要为排查助手建一套评测。现有资源：30 个历史案例（含真实根因）、脱敏的日志/图像/配置、一台测试设备（可人为制造故障）。

## 题目

**Q1（范式与词汇，20 分）**
（a）课件说「agent 是通过评估开发的，不是从数据训练的」。用你的场景解释这句话为什么成立。
（b）定义以下术语并用你的场景举例：Task、Trial、Benchmark、Verifier、Trajectory、Evaluation Harness、Agent Harness。
（c）Evaluation Harness 和 Agent Harness 在你的场景里分别是什么？谁启动谁？

**Q2（写任务，30 分）**
（a）列出好 task 的五个性质，并说明每个性质在你的场景里怎么满足。
（b）为一个具体故障场景（自选，例如「夜间残差升高」）写出完整的 task 五件套：
- instruction.md 的全文（注意选哪种指令风格，并说明为什么）
- task.toml 的关键字段
- environment 里需要什么（不写 Dockerfile，写清单）
- solution/solve.sh 的步骤（必须是模仿 agent 的动作，不能硬编码）
- tests/test.sh 的检查点
（c）instruction 的三种风格各测什么？你的 task 选了哪种？为什么不能混用？

**Q3（写验证器，30 分）**
（a）为什么验证器要「看结果不看过程」？「基于环境状态」排除了什么错误做法？
（b）画出你场景的混淆矩阵，说明 FP 和 FN 各自的危害。哪个更危险？
（c）设计四层验证器：格式检查、结论命中、证据检查、安全性检查。每层具体检查什么？为什么这个顺序？
（d）防奖励黑客的四道隔离是什么？在你的场景里具体怎么做？
（e）参考解为什么必须模仿 agent 动作而不能直接 echo 答案？举一个它能发现的 bug。

**Q4（基础设施与持续维护，20 分）**
（a）评测基建的四个要求是什么？在你的单机环境下怎么满足「可复现」和「快」？
（b）「任务是软件，软件有 bug」——你的基准会以哪四种方式腐烂？各举你场景的具体例子。
（c）regrade / rerun / reuse 三档各适用什么情况？举两个你场景里属于不同档的改动。
（d）「每行结果都要有完整凭据」——你要存什么？为什么没有凭据的评测等于没有评测？
